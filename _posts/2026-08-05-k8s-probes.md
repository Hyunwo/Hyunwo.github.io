지난 글에서 정리한 Pod 라이프사이클(Phase, Conditions, Container State)은 readiness probe와 liveness probe를 이해하는 전제가 된다. 두 probe 모두 "Pod는 Running인데 실제로는 문제가 있는" 상황을 다루는 기능이다.

## Readiness Probe: Running인데 아직 준비가 안 됐을 때

시나리오로 보면 이해가 빠르다. 한 Service에 Pod 2개가 붙어서 트래픽을 50:50으로 나눠 받고 있다고 하자.

- Node 2가 다운되면서 그 위의 Pod 2도 죽고, 사용자는 전부 Pod 1로 접속하게 된다
- 죽은 Pod 2는 오토 힐링으로 다른 Node에 재생성되는데, Pod와 컨테이너가 Running이 되는 시점과 그 안의 앱이 완전히 뜨는 시점 사이에 간격이 있다
- 문제는 **Service는 Pod가 Running이 되자마자 바로 트래픽을 보낸다는 것.** 앱이 아직 준비 중인 그 짧은 순간에 트래픽이 들어가면, 사용자는 50% 확률로 에러 페이지를 보게 된다

![Readiness Probe 유무 차이]({{ site.baseurl }}/assets/images/k8s-probes/readiness_probe_scenario.png)

readinessProbe를 걸어두면 이 문제를 피할 수 있다. **앱이 완전히 준비됐다고 확인되기 전까지는 Service와 연결되지 않기 때문**이다. Pod 2의 Phase는 Running이지만 `Ready` Condition이 False인 동안에는, 엔드포인트가 이 Pod의 IP를 "Not Ready Address"로 취급해서 트래픽을 안 보낸다. 그동안 트래픽은 계속 Pod 1에만 가고, 앱이 준비된 게 확인되면 그제서야 다시 50:50으로 돌아간다.

## Liveness Probe: Running인데 앱이 멈춰있을 때

readiness probe로도 못 잡는 상황이 있다. Tomcat 위에 앱을 올려서 서비스하는 경우를 생각해보자. 앱에 메모리 오버플로우 같은 문제가 생겨서 500 Internal Server Error를 계속 뱉어도, **Tomcat 프로세스 자체는 안 죽었기 때문에 Pod 입장에서는 계속 Running으로 보인다.** Pod는 멀쩡해 보이는데 실제로는 트래픽을 받을 때마다 에러가 나는 상황이다.

이걸 잡아주는 게 livenessProbe다. 앱에 문제가 생긴 걸 감지하면 **컨테이너를 재시작**시켜서, 지속적인 에러 상태를 막아준다.

![Liveness Probe 동작 흐름]({{ site.baseurl }}/assets/images/k8s-probes/liveness_probe_flow.png)

> 여기서 "재시작"은 이전 글에서 정리한 **Restart** 방식이다. Pod가 통째로 삭제되고 새로 만들어지는 Recreate와 달리, 컨테이너만 다시 기동되기 때문에 Pod 이름과 IP는 그대로 유지된다.

정리하면, **readiness probe는 앱이 뜨는 순간의 일시적인 트래픽 실패를 막아주고, liveness probe는 앱이 멈춘 뒤의 지속적인 실패를 막아준다.** 둘 다 실무에서는 기본으로 걸어두는 게 좋다.

## 설정 방법: 공통 속성

readiness probe와 liveness probe는 목적만 다를 뿐, 설정할 수 있는 속성은 동일하다.

### 체크 방식 3가지 (+ 최신 1가지)

셋 중 하나는 반드시 정해야 한다.

| 방식 | 설명 |
|---|---|
| **httpGet** | 지정한 포트/경로로 HTTP 요청을 보내 응답을 확인. port, host, path, httpHeaders, scheme 등을 세부 설정 가능 |
| **exec** | 컨테이너 안에서 특정 명령어를 실행해서 결과(종료 코드)로 확인 |
| **tcpSocket** | 지정한 포트로 TCP 연결이 되는지 확인. port, host 설정 |
| **grpc** | gRPC Health Checking Protocol로 확인. Kubernetes 1.27부터 정식 기능(stable)으로 추가됨 |

강의에는 없었지만, gRPC로 통신하는 서비스를 다룬다면 이제 이 방식도 선택지에 들어간다.

### 타이밍/판정 옵션

| 옵션 | 의미 |
|---|---|
| **initialDelaySeconds** | 최초 probe를 실행하기 전 대기 시간 |
| **periodSeconds** | probe를 반복하는 간격 |
| **timeoutSeconds** | probe 결과가 이 시간 안에 와야 함 |
| **successThreshold** | 몇 번 연속 성공해야 진짜 성공으로 인정할지 |
| **failureThreshold** | 몇 번 연속 실패해야 진짜 실패로 인정할지 |

값을 따로 안 넣으면 각 옵션의 기본값이 적용된다.

![Probe 옵션별 기본값]({{ site.baseurl }}/assets/images/k8s-probes/probe_defaults.png)

## Readiness Probe 예시

exec 방식으로 `ready.txt` 파일이 있는지 확인하는 설정이다.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: web-pod
spec:
  containers:
    - name: web
      image: my-web-app
      volumeMounts:
        - name: shared-data
          mountPath: /data
      readinessProbe:
        exec:
          command: ["cat", "/data/ready.txt"]
        initialDelaySeconds: 5
        periodSeconds: 10
        successThreshold: 3
  volumes:
    - name: shared-data
      hostPath:
        path: /mnt/data
```

동작 흐름은 이렇다.

1. Node 스케줄링 → 이미지 다운로드가 끝나면 Pod와 컨테이너는 `Running`이 되지만, probe가 성공하기 전까지 `ContainersReady`/`Ready` Condition은 계속 False
2. Running 진입 후 5초(`initialDelaySeconds`) 대기
3. `ready.txt`를 조회 → 없으면 10초(`periodSeconds`) 후 재시도
4. 볼륨에 `ready.txt`가 추가되면 다음 체크에서 성공
5. 3회 연속 성공(`successThreshold`)하면 Condition이 True로 바뀌고, 엔드포인트가 이 Pod를 정상 address로 인식해서 Service와 연결

## Liveness Probe 예시

`/health` 경로로 HTTP GET을 보내서 확인하는 설정이다.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: web-pod
spec:
  containers:
    - name: web
      image: my-web-app
      livenessProbe:
        httpGet:
          path: /health
          port: 8080
        initialDelaySeconds: 5
        periodSeconds: 10
        failureThreshold: 3
```

앱에 `/health` 경로가 있고, 정상일 때는 200 OK를 준다고 하자.

1. Running 진입 후 5초 대기, `/health` 체크 → 200 OK
2. 10초 뒤 다시 체크 → 200 OK, 정상 운영 중으로 판단
3. 어느 시점에 앱에 문제가 생겨 500 Error를 받기 시작. 이 순간에도 Pod Phase는 여전히 `Running`
4. 500 Error가 3회(`failureThreshold`) 연속되면 Kubernetes가 문제로 판단하고 **컨테이너를 재시작**

## 다음에 볼 것: startupProbe

이번 강의에는 없었지만, readiness/liveness probe와 같이 다니는 **startupProbe**라는 것도 있다. 컨테이너가 뜨는 데 시간이 오래 걸리는 앱에서, readiness/liveness probe가 너무 일찍 실패로 판단해버리는 걸 막기 위한 probe다. startupProbe가 성공하기 전까지는 readiness/liveness probe 자체가 아예 시작되지 않는다. 다음 강의에서 다룰 것 같은데, 미리 이름 정도는 알아두면 좋을 것 같다.

## 용어 정리

| 용어 | 설명 |
|---|---|
| **readinessProbe** | 컨테이너가 트래픽을 받을 준비가 됐는지 확인하는 probe. 실패 시 Service 트래픽 대상에서 제외됨 |
| **livenessProbe** | 컨테이너가 정상적으로 살아있는지 확인하는 probe. 실패 시 컨테이너가 재시작됨 |
| **startupProbe** | 느리게 시작하는 컨테이너를 위한 probe. 이게 성공하기 전까지 readiness/liveness probe는 대기함 |
| **httpGet / exec / tcpSocket / grpc** | probe의 체크 방식. grpc는 Kubernetes 1.27부터 stable |
| **initialDelaySeconds** | probe 최초 실행 전 대기 시간 |
| **periodSeconds** | probe 반복 간격 |
| **timeoutSeconds** | probe 결과를 기다리는 최대 시간 |
| **successThreshold** | 연속 성공으로 인정하기 위한 횟수 |
| **failureThreshold** | 연속 실패로 인정하기 위한 횟수 |
| **Not Ready Address** | readinessProbe가 실패한 Pod의 IP를 엔드포인트가 분류하는 상태. Service 트래픽 대상에서 제외됨 |
