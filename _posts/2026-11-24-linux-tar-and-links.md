이 글은 두 가지 주제를 다룬다. 하나는 여러 파일과 폴더를 하나로 묶고 압축해 보관하는 `tar`이고, 다른 하나는 같은 파일을 여러 이름으로 가리키는 심볼릭 링크와 하드 링크다. `tar`는 명령어 사용법을 익히면 바로 쓸 수 있지만, 링크는 "복사하면 되는데 왜 굳이 링크를 쓰는가"라는 의문이 남기 쉽다. 그래서 링크 부분은 동작 원리, 직접 해 보는 실습, 실제 서버와 컨테이너에서 링크가 쓰이는 장면, 자주 하는 실수까지 나누어 자세히 정리한다.

## tar로 여러 파일 묶고 풀기

파일이 많으면 하나씩 옮기기 번거롭다. 이때는 여러 파일과 폴더 구조를 하나의 보관 파일, 즉 **아카이브**로 묶는다. 용어를 먼저 구분해 두면 혼동이 줄어든다.

- **묶기**: 여러 자료를 하나로 모으는 일. 이사 상자 하나에 물건을 담는 것과 같다.
- **압축**: 저장할 데이터의 크기를 줄이는 일. 압축팩으로 공간을 줄이는 것과 같다.
- 폴더 구조도 함께 보관하므로, 풀면 파일이 있던 위치까지 되살아난다.

`tar`는 묶기를 담당하고, `-z` 옵션을 붙이면 gzip 압축까지 함께 처리한다.

```bash
# 1. 묶고 gzip으로 압축
tar -czf archive-lab/notes-bundle.tar.gz notes todo.txt

# 2. 풀지 않고 내부 목록 확인
tar -tzf archive-lab/notes-bundle.tar.gz

# 3. 빈 폴더에 풀기
tar -xzf archive-lab/notes-bundle.tar.gz -C restore-lab

# 4. 원본과 비교
diff -rs notes restore-lab/notes
diff -s todo.txt restore-lab/todo.txt
```

옵션을 하나씩 풀어 보면 다음과 같다.

| 옵션 | 의미 |
|---|---|
| `-c` | 새 보관 파일을 만든다 |
| `-t` | 풀지 않고 안에 든 파일과 폴더 이름만 본다 |
| `-x` | 보관 파일에서 자료를 꺼낸다 |
| `-z` | gzip 방식으로 압축하거나, 그 방식으로 압축된 자료를 푼다 |
| `-f` | 바로 다음에 적은 이름을 보관 파일 이름으로 쓴다 |
| `-C` | 뒤에 적은 폴더에서 작업한다. 풀 때는 목적지 폴더를 정한다 |

`-f` 바로 뒤에는 보관 파일의 경로가 와야 하므로 `-czf`처럼 `f`를 옵션 묶음의 맨 끝에 둔다. 새로 묶을 때는 보관 파일 경로 뒤에 담을 파일과 폴더를 적고, 폴더를 지정하면 그 안의 파일도 함께 묶인다. `-C`를 생략하면 현재 폴더에 풀리므로 기존 파일과 이름이 겹칠 수 있다. 풀기 전에 목적지에 다른 자료가 없는지 확인하고, 가능하면 빈 폴더를 쓴다.

### 묶은 뒤에는 목록과 복원본을 확인한다

상자를 포장했다고 끝이 아니라, 안에 무엇이 들었는지 보고 제대로 꺼낼 수 있어야 한다. 그래서 순서가 정해져 있다.

1. 묶을 원본을 확인하고 보관 파일을 만든다.
2. `tar -t`로 목록을 보며 빠진 자료는 없는지, 의도하지 않은 자료가 들어가지는 않았는지 살핀다.
3. 기존 자료와 섞이지 않도록 빈 폴더에 푼다.
4. 풀린 폴더 구조와 파일 내용을 원본과 비교한다.

원본, 보관 파일, 풀어서 얻은 복원본은 서로 다른 대상이다. 압축을 풀어도 원본이나 보관 파일이 자동으로 없어지지 않으며, 보관 파일은 만든 시점의 자료만 담고 있다. 나중에 원본 메모를 고쳐도 이미 만든 압축 파일의 내용은 바뀌지 않는다.

크기에 대해서도 알아 둘 점이 있다. 아주 작은 자료는 이름과 구조를 기록하는 정보 때문에 압축 후에 오히려 원본보다 커질 수 있다. `ls -lh`에서 `377`처럼 단위 없이 숫자만 보이면 바이트 단위라는 뜻이고, `total 4.0K`는 파일 크기가 아니라 디스크에 할당된 공간의 합계다. 디스크는 일정한 블록 단위로 공간을 할당하므로 둘이 다를 수 있다.

### diff 결과 해석

`diff`는 두 대상의 내용 차이를 비교한다. `-r`은 폴더 안쪽까지, `-s`는 내용이 같은 파일도 같다고 보고하는 옵션이다.

```text
Files notes/day1.txt and restore-lab/notes/day1.txt are identical
```

이 메시지는 두 위치에 있는 메모의 **내용**이 동일하다는 뜻이다. 소유자나 권한 같은 모든 속성이 같다는 보장은 아니다. 차이가 없으면 `diff`는 아무것도 출력하지 않기 때문에, `-s`를 붙여야 "같다"는 결과가 눈에 보인다.

### tar를 실무에서 쓰는 방식

실습에서는 메모 파일을 묶었지만, 서버에서는 다음 상황에서 자주 쓴다.

```bash
# 설정을 바꾸기 전에 날짜가 들어간 백업을 만든다
sudo tar -czf ~/nginx-conf-20261124.tar.gz /etc/nginx

# 압축할 때 특정 파일은 제외한다
tar -czf project.tar.gz --exclude='*.log' project/

# 묶는 과정을 자세히 보려면 -v를 붙인다
tar -czvf project.tar.gz project/
```

절대 경로(`/etc/nginx`)를 묶으면 GNU tar는 `Removing leading '/' from member names`라는 메시지를 띄우며 맨 앞의 `/`를 떼고 저장한다. 풀 때 시스템 폴더를 의도치 않게 덮어쓰는 일을 막기 위한 동작이다. 압축 방식은 gzip(`-z`) 외에 xz(`-J`), bzip2(`-j`)도 있고, 일반적으로 gzip이 가장 빠르고 널리 쓰인다. 컨테이너 이미지의 각 레이어도 내부적으로 tar 아카이브이므로, `tar`를 익혀 두면 이미지 구조를 이해하는 데도 도움이 된다.

`tar`는 링크도 그대로 보관한다. 심볼릭 링크는 링크 형태로 저장되고(가리키는 대상 파일을 저장하려면 `-h` 옵션을 쓴다), 같은 파일에 연결된 하드 링크는 내용을 한 번만 저장한 뒤 나머지 이름은 링크 정보로 기록한다. 이 동작을 이해하려면 링크가 무엇인지부터 알아야 한다.

## 링크는 왜 필요한가

링크를 이해하는 열쇠는 "파일 이름"과 "파일 자체"가 다른 것이라는 점이다. 파일시스템은 파일 자체를 **inode**라는 관리 정보로 구분한다. inode에는 파일의 속성(소유자, 권한, 크기, 시간)과 데이터가 디스크 어디에 있는지가 담겨 있다. 우리가 보는 파일 이름은 폴더가 가진 목록에서 "이 이름은 이 inode 번호를 가리킨다"고 적어 둔 항목이다.

```text
폴더 (이름 → inode 번호 목록)
 ├─ source.txt → inode 1048600 ─┐
 └─ hard.txt   → inode 1048600 ─┴→ 같은 파일 (속성과 데이터 위치)
```

이 구조 덕분에 두 가지 방식으로 "같은 내용을 다른 이름으로" 열 수 있다.

- **하드 링크**: 폴더 목록에 같은 inode 번호를 가리키는 이름을 하나 더 추가한다.
- **심볼릭 링크**: "이 경로로 가라"는 문자열만 담은 별도의 작은 파일을 만든다. inode가 따로 있다.

복사는 데이터까지 한 벌 더 만들기 때문에 원본을 고쳐도 복사본이 바뀌지 않는다. 링크는 데이터를 늘리지 않고 접근 경로만 늘린다. 이 차이가 링크의 쓰임새를 결정한다. 복사본이 아니라 "원본 하나를 여러 곳에서 같은 것으로 보이게 하는" 용도라면 링크가 맞다.

## 심볼릭 링크와 하드 링크 만들고 확인하기

비유로 정리하면, 심볼릭 링크는 "자료는 옆방 서랍에 있다"고 적은 **안내표**이고 하드 링크는 하나의 보관함에 붙은 **이름표 두 개**다.

```bash
ln -s source.txt shortcut.txt    # 심볼릭 링크 생성
ln source.txt hard.txt           # 하드 링크 생성 (-s 생략)
```

`ln`은 먼저 연결할 대상의 경로를, 다음에 새 링크 이름을 쓴다. 파일을 복사하는 `cp 원본 새이름`과 같은 순서다.

### inode 번호로 같은 파일 확인

```bash
ls -li source.txt hard.txt shortcut.txt
```

`-i`는 목록 맨 앞에 inode 번호를 붙인다. 이미 배운 `-l`과 합쳐 `-li`로 쓴다.

```text
1048600 -rw-rw-r-- 2 ubuntu ubuntu 12 Nov 24 10:20 hard.txt
1048601 lrwxrwxrwx 1 ubuntu ubuntu 10 Nov 24 10:20 shortcut.txt -> source.txt
1048600 -rw-rw-r-- 2 ubuntu ubuntu 12 Nov 24 10:20 source.txt
```

위 출력은 구조를 보여 주기 위한 예시이고 숫자는 환경마다 다르다. 읽을 때 볼 지점은 세 가지다.

- `source.txt`와 `hard.txt`의 inode 번호가 같다. 같은 파일에 붙은 두 이름이라는 증거다.
- `shortcut.txt`는 번호가 다르고, 맨 앞 글자가 `l`이며, 화살표로 `source.txt`를 가리킨다. 메모의 복사본이 아니라 다른 경로를 가리키는 별도 항목이다.
- 권한 뒤의 숫자(`2`)는 그 파일에 연결된 이름의 개수(링크 수)다. 하드 링크를 만들면 늘어난다.

그 외에 `stat source.txt`로 링크 수(`Links`)와 inode를 함께 볼 수 있고, `find . -samefile source.txt`로 같은 파일에 붙은 이름을 모두 찾을 수 있다.

### 대상 이름을 바꾸면 각 링크는 어떻게 되는가

두 링크의 차이는 대상의 이름을 바꾸거나 지울 때 분명히 드러난다.

```bash
mv source.txt renamed.txt
cat hard.txt        # 정상적으로 열린다
cat shortcut.txt    # 대상을 찾지 못한다 (깨진 링크)
```

하드 링크는 `source.txt`라는 경로를 거쳐 읽는 것이 아니라 같은 파일에 붙은 또 하나의 이름이므로, 이름이 바뀌어도 계속 사용할 수 있다. 반면 심볼릭 링크는 적힌 경로로 찾아가기 때문에, 그 경로에 대상이 없어지면 **깨진 링크**가 된다. 링크 자체는 남아 있지만 가리키는 대상을 찾지 못하는 상태다.

링크가 열리지 않을 때는 파일이 사라졌다고 단정하지 말고, 화살표가 가리키는 경로에 대상이 있는지부터 확인한다. 고치려면 같은 링크 이름으로 새 경로를 가리키게 다시 만든다.

```bash
ln -sf renamed.txt shortcut.txt    # -f: 같은 이름의 기존 링크를 교체
```

`-f` 없이 실행하면 같은 이름이 이미 있어 실패한다. `-f`는 확인 없이 교체하는 옵션이므로 이름을 정확히 확인한 뒤 쓴다.

### 삭제해도 남는 것과 사라지는 것

```bash
rm -i renamed.txt
```

- 심볼릭 링크를 `rm`으로 지우면 링크 자체만 제거된다. 가리키던 대상 파일은 지워지지 않는다.
- `rm`은 지정한 **이름**만 제거한다. 다른 하드 링크가 남아 있으면 그 이름으로 같은 파일을 계속 쓸 수 있다. `renamed.txt`를 지워도 `hard.txt`는 그대로 보인다.
- 하드 링크끼리는 어느 쪽이 원본이고 어느 쪽이 부속인지 구별되지 않는다. 먼저 만든 이름이 반드시 남아 있어야 하는 것은 아니다.
- 반대로 심볼릭 링크가 남아 있다는 사실이 대상 파일의 내용을 보존해 주지는 않는다.

### 두 링크 비교

| 비교 항목 | 심볼릭 링크 | 하드 링크 |
|---|---|---|
| 저장하는 것 | 대상의 경로 | 같은 파일에 붙은 이름 |
| 생성 | `ln -s 대상 링크이름` | `ln 대상 링크이름` |
| inode 번호 | 대상과 다르다 | 대상과 같다 |
| 대상 이름 변경 시 | 깨진 링크가 된다 | 계속 사용할 수 있다 |
| 폴더에 사용 | 가능 | 일반적으로 불가능 |
| 다른 파일시스템 사이 | 가능 | 불가능 |
| 대상이 없는 상태 | 만들 수 있다(깨진 링크) | 만들 수 없다 |
| `rm`으로 지우면 | 링크만 제거된다 | 그 이름만 제거되고, 다른 이름이 있으면 내용은 유지된다 |

## 현업에서 심볼릭 링크는 어디에 쓰이는가

심볼릭 링크의 핵심 가치는 **"바뀌는 실제 위치를 고정된 이름 뒤에 숨기는 것"**이다. 사용하는 쪽(프로그램, 설정, 다른 사람)은 고정된 이름만 알고, 관리하는 쪽은 링크가 가리키는 곳만 바꿔 동작을 전환한다. 아래 장면들은 모두 이 한 가지 아이디어의 변형이다.

### 배포 버전을 전환하고 되돌릴 때

서버에 애플리케이션을 배포할 때 흔한 구조다.

```text
/opt/myapp/
 ├─ releases/
 │   ├─ 20261120/   ← 이전 버전
 │   └─ 20261124/   ← 새 버전
 └─ current → releases/20261124      ← 서비스는 항상 이 경로로 실행
```

서비스 설정(systemd 유닛 등)은 항상 `/opt/myapp/current/...`만 바라본다. 새 버전을 배포하면 새 폴더를 만들고 `current`가 가리키는 곳만 바꾸면 되고, 문제가 생기면 이전 폴더로 되돌리면 끝이다. 파일을 덮어쓰지 않으므로 이전 버전이 그대로 남아 롤백이 빠르다. 직접 해 보면 구조가 바로 이해된다.

```bash
mkdir -p ~/linux-lab/deploy-lab/releases/v1 ~/linux-lab/deploy-lab/releases/v2
cd ~/linux-lab/deploy-lab
echo "version 1" > releases/v1/app.txt
echo "version 2" > releases/v2/app.txt

ln -s releases/v1 current
cat current/app.txt              # version 1

# v2로 전환: 임시 링크를 만든 뒤 이름을 바꿔치기
ln -s releases/v2 current.tmp
mv -T current.tmp current
cat current/app.txt              # version 2

# 롤백: v1을 가리키게 다시 전환
ln -s releases/v1 current.tmp
mv -T current.tmp current
ls -l
```

`ln -sf`로 직접 교체하지 않고 임시 링크를 만들어 `mv -T`로 바꿔치기하는 이유가 있다. `ln -sf`는 기존 링크를 지운 뒤 새로 만드는 방식이라 두 동작 사이에 링크가 없는 짧은 순간이 생길 수 있다. 반면 `mv`는 이름 바꾸기 한 번으로 처리되어 중간 상태가 보이지 않는다. 또 `current`는 폴더를 가리키는 링크이므로 `-T`(대상을 폴더로 취급하지 않음)를 붙이지 않으면 `mv`가 링크를 교체하는 대신 가리키는 폴더 안으로 옮겨 버린다. 다만 이미 실행 중인 프로세스는 옛 파일을 열고 있으므로, 링크를 바꾼 뒤에는 서비스를 재시작하거나 다시 불러와야 새 버전이 적용된다.

### 설정을 켜고 끄는 방식으로 쓸 때

Ubuntu에서 nginx를 설치하면 설정 폴더가 둘로 나뉜다.

```text
/etc/nginx/sites-available/   ← 만들어 둔 설정 파일 전체 (켜진 것과 꺼진 것)
/etc/nginx/sites-enabled/     ← 실제로 적용할 설정 (available 파일을 가리키는 링크)
```

사이트를 켜려면 `sites-enabled`에 링크를 만들고, 끄려면 링크만 지우면 된다. 설정 파일 원본은 `sites-available`에 그대로 남는다.

```bash
sudo ln -s /etc/nginx/sites-available/myapp /etc/nginx/sites-enabled/myapp
sudo nginx -t                    # 설정 문법 검사
sudo systemctl reload nginx      # 무중단 반영
```

`systemctl enable 서비스이름`도 같은 원리다. 실행하면 `Created symlink /etc/systemd/system/multi-user.target.wants/...` 메시지가 나오는데, 서비스를 부팅 시 자동 시작하도록 "켜는" 동작이 실제로는 링크 하나를 만드는 일이다. `disable`은 그 링크를 지운다.

### 같은 기능을 하는 여러 프로그램 중 하나를 고를 때

`/usr/bin/editor`는 "기본 편집기"를 뜻하는 고정 이름이고, 실제 프로그램은 링크를 두 단계 거쳐 정해진다.

```bash
ls -l /usr/bin/editor /etc/alternatives/editor
# /usr/bin/editor -> /etc/alternatives/editor
# /etc/alternatives/editor -> /usr/bin/nano  (환경에 따라 다름)
```

`update-alternatives` 명령이 이 링크를 관리한다. Java나 Python처럼 버전이 여러 개 설치될 수 있는 도구에서 "기본 버전"을 바꿀 때도 같은 방식이 쓰인다. 사용자는 `editor`, `java` 같은 고정된 이름만 입력하면 된다.

### 시스템에 이미 있는 링크

서버에는 직접 만들지 않아도 링크가 곳곳에 이미 있다. 아래 명령으로 직접 확인해 보면 링크가 얼마나 일상적인지 알 수 있다.

```bash
ls -l /etc/localtime        # 시간대: /usr/share/zoneinfo/... 중 하나를 가리킨다
ls -ld /bin                 # /bin -> usr/bin (최근 Ubuntu 기준)
ls -l /etc/resolv.conf      # Ubuntu에서는 systemd-resolved가 관리하는 파일을 가리킨다
readlink -f "$(which python3)"   # 링크를 끝까지 따라가 실제 파일 경로를 출력
```

`/etc/localtime`이 좋은 예다. 서버의 시간대를 바꾸는 `sudo timedatectl set-timezone Asia/Seoul`을 실행하면 이 링크가 `/usr/share/zoneinfo/Asia/Seoul`을 가리키도록 바뀐다. 시간대 데이터 파일을 복사하는 것이 아니라 "지금 쓸 시간대는 이것"이라는 가리킴만 바꾸는 방식이다.

프로그램이 실행할 때 불러오는 공유 라이브러리에서도 같은 패턴이 쓰인다. 라이브러리는 보통 `libfoo.so.1.2.3`처럼 정확한 버전이 붙은 실제 파일과, `libfoo.so.1` 같은 짧은 이름의 링크로 구성된다. 프로그램은 짧은 이름만 찾고, 패치 버전이 올라가면 링크만 새 파일로 옮긴다.

### 디스크 용량이 부족할 때

로그나 데이터 폴더가 커져 디스크가 가득 차면, 더 큰 디스크로 폴더를 옮기고 원래 경로에 링크를 남기는 방법이 있다.

```bash
sudo systemctl stop myapp
sudo mv /var/log/myapp /data/log/myapp
sudo ln -s /data/log/myapp /var/log/myapp
sudo systemctl start myapp
```

프로그램은 여전히 `/var/log/myapp`에 쓰지만 실제 데이터는 큰 디스크에 쌓인다. 다만 서비스를 멈추고 작업해야 하고, 옮긴 폴더의 소유자와 권한이 유지되는지 확인해야 한다. 프로그램이 설정으로 데이터 경로를 직접 지정할 수 있다면 링크보다 설정을 바꾸는 쪽이 더 명확하고, 별도 디스크를 해당 경로에 마운트하는 방법도 있다. 링크는 "설정을 바꿀 수 없는 프로그램을 우회할 때" 쓰는 수단으로 이해해 두면 된다.

### 컨테이너와 쿠버네티스에서

쿠버네티스를 공부하고 있다면 링크를 이미 간접적으로 만났을 가능성이 높다.

- **공식 nginx 이미지의 로그**: 이미지는 `/var/log/nginx/access.log`를 `/dev/stdout`으로 연결하는 링크로 만든다(Dockerfile의 `ln -sf /dev/stdout ...`). nginx는 평소처럼 파일에 쓰지만 실제로는 표준 출력으로 흘러가므로 `kubectl logs`와 `docker logs`로 볼 수 있다. 로그 파일을 따로 관리할 필요가 없어지는 이유다.
- **노드의 컨테이너 로그**: 쿠버네티스 노드의 `/var/log/containers/` 아래 로그 파일은 `/var/log/pods/...` 쪽 실제 로그를 가리키는 링크다. Fluent Bit 같은 로그 수집기가 이 경로를 읽는다.
- **ConfigMap 볼륨**: ConfigMap을 볼륨으로 마운트한 폴더에서 `ls -la`를 하면 `app.conf -> ..data/app.conf`, `..data -> ..2026_11_24_...` 같은 링크 구조가 보인다. ConfigMap이 바뀌면 새 타임스탬프 폴더를 만든 뒤 `..data` 링크만 새 폴더로 바꿔치기해서, 앞의 배포 사례와 같은 방식으로 파일 내용이 한 번에 갱신된다. `subPath`로 마운트한 파일은 이 링크 구조를 거치지 않아 ConfigMap이 바뀌어도 자동 갱신되지 않는다.

### 심볼릭 링크 사용 사례 요약

| 상황 | 링크가 하는 일 | 바꾸는 것 |
|---|---|---|
| 배포 전환·롤백 | 고정 경로 `current`가 버전 폴더를 가리킨다 | 링크 대상 |
| nginx 사이트, systemd 서비스 | 링크가 있으면 켜짐, 없으면 꺼짐 | 링크 생성·삭제 |
| 기본 편집기, Java 버전 | 고정 이름이 선택된 프로그램을 가리킨다 | 링크 대상 |
| 시간대, 공유 라이브러리 | 고정 이름이 현재 쓸 파일을 가리킨다 | 링크 대상 |
| 디스크 용량 우회 | 옛 경로가 새 디스크의 폴더를 가리킨다 | 데이터 위치 |
| 컨테이너 로그, ConfigMap | 읽는 쪽 경로는 그대로, 실제 위치는 다른 곳 | 가리키는 곳 |

## 현업에서 하드 링크가 쓰이는 곳

하드 링크는 직접 만들어 쓰는 일이 심볼릭 링크보다 훨씬 적다. 그 대신 **원리를 알아야 이해되는 현상**이 있고, 몇몇 도구가 내부에서 활용한다. 핵심 가치는 "같은 데이터를 디스크에 한 번만 저장하면서 여러 이름으로 완전한 파일처럼 보이게 하는 것"이다.

### 증분 백업에서 디스크를 아끼며 스냅샷을 만들 때

매일 전체 백업을 만들면 거의 똑같은 파일이 날마다 쌓인다. `rsync --link-dest`나 rsnapshot은 바뀌지 않은 파일을 하드 링크로 연결해서, 각 날짜의 백업 폴더가 완전한 사본처럼 보이면서도 실제 디스크는 바뀐 파일만큼만 쓴다. 직접 확인해 보자(`rsync`가 없으면 `sudo apt install rsync`).

```bash
mkdir -p ~/linux-lab/backup-lab/src && cd ~/linux-lab/backup-lab
echo "hello" > src/a.txt
echo "world" > src/b.txt

rsync -a src/ snap1/                          # 첫 번째 백업
echo "changed" > src/b.txt                    # b.txt만 변경
rsync -a --link-dest=../snap1 src/ snap2/     # 두 번째 백업

ls -li snap1 snap2
```

결과에서 `a.txt`는 `snap1`과 `snap2`의 inode 번호가 같고(디스크에 한 벌), 바뀐 `b.txt`만 번호가 다르다. `--link-dest` 경로는 백업을 만드는 폴더(`snap2`)를 기준으로 해석되므로 `../snap1`이다. 어느 날짜의 폴더를 지워도 다른 날짜의 파일은 영향을 받지 않는다. 하드 링크에는 원본과 부속의 구분이 없기 때문이다.

### 파일을 지웠는데 디스크 공간이 돌아오지 않을 때

서버 운영에서 가장 자주 마주치는 하드 링크 관련 상황이다. 로그 파일이 커져서 `rm`으로 지웠는데 `df`로 보면 여전히 디스크가 가득 차 있는 경우가 있다. 파일은 **이름이 모두 사라지고, 파일을 열고 있는 프로세스도 없을 때** 비로소 디스크에서 지워지기 때문이다. `rm`은 이름 하나를 제거할 뿐이고, 어떤 프로세스가 아직 그 파일을 열고 있으면 데이터는 남는다. 직접 재현해 볼 수 있다.

```bash
dd if=/dev/zero of=~/big.dat bs=1M count=50   # 50MB 파일 생성
tail -f ~/big.dat > /dev/null &               # 파일을 열고 있는 프로세스
rm ~/big.dat                                  # 이름 삭제

ls -l /proc/$!/fd | grep big                  # 'big.dat (deleted)'로 표시된다
kill $!                                       # 프로세스를 끝내면 공간이 반환된다
```

실제 서버에서는 `sudo lsof +L1`(링크 수가 0인데 열려 있는 파일 조회)로 찾을 수 있고, 해결 방법은 그 프로세스를 재시작하거나 다시 열게 하는 것이다. 이런 문제를 피하려고 로그를 지울 때는 파일을 삭제하지 않고 내용만 비우는 방식(`: > 파일`)을 쓰기도 한다. 하드 링크의 "이름과 파일은 별개"라는 개념을 알면 이 현상이 바로 이해된다.

### 도구가 내부에서 사용하는 경우

- **pnpm**: 패키지를 한 곳의 저장소에 두고 각 프로젝트의 `node_modules`에는 하드 링크로 연결해, 프로젝트가 늘어나도 디스크 사용량이 크게 늘지 않는다. 저장소와 프로젝트가 같은 파일시스템에 있을 때 이 방식이 동작한다.
- **git clone**: 같은 컴퓨터 안의 저장소를 복제할 때 기본적으로 객체 파일을 하드 링크로 공유해 빠르고 공간을 아낀다.
- **폴더의 링크 수**: `ls -ld notes`를 보면 폴더의 링크 수가 2 이상으로 나온다. 폴더 자신의 이름과 그 안의 `.`이 같은 폴더를 가리키는 하드 링크이기 때문이다. 일반적인 ext4 파일시스템에서는 하위 폴더가 하나 늘 때마다 `..` 때문에 상위 폴더의 링크 수가 1씩 늘어난다.

### 하드 링크는 언제 쓰고 언제 쓰지 않는가

| 하고 싶은 일 | 선택 | 이유 |
|---|---|---|
| 폴더를 가리키는 경로를 하나 더 만들기 | 심볼릭 링크 | 하드 링크는 폴더에 쓸 수 없다 |
| 다른 디스크(파일시스템)의 파일을 가리키기 | 심볼릭 링크 | 하드 링크는 같은 파일시스템 안에서만 가능하다 |
| 버전 전환, 설정 켜고 끄기 | 심볼릭 링크 | 링크 대상을 바꿔 동작을 전환한다 |
| 이름이 바뀌거나 지워져도 내용이 유지되어야 함 | 하드 링크 | 이름 중 하나가 남아 있으면 파일이 유지된다 |
| 같은 내용을 디스크에 한 번만 저장하며 여러 곳에 두기 | 하드 링크 | 스냅샷 백업, 패키지 저장소 방식 |
| 일반적인 파일 사본이 필요함(각자 수정) | 복사(`cp`) | 한쪽을 고쳐도 다른 쪽이 그대로여야 하기 때문 |

하드 링크는 이름이 달라도 **같은 파일**이므로, 한 이름으로 내용을 고치면 다른 이름으로도 고친 내용이 보인다. 독립된 사본이 필요한 상황에 하드 링크를 쓰면 의도치 않게 같이 바뀐다.

## 링크를 쓸 때 자주 하는 실수

### 인수 순서를 거꾸로 적는다

`ln -s 대상 링크이름` 순서다. 헷갈리면 `cp 원본 새이름`과 같은 순서로 기억한다. 거꾸로 적으면 의도와 다른 이름의 링크가 생기거나 오류가 난다.

### 상대 경로의 기준을 현재 위치로 착각한다

상대 경로로 만든 심볼릭 링크는 링크가 **놓인 폴더**를 기준으로 대상을 찾는다. 현재 폴더 기준이 아니다.

```bash
ln -s ../data/app.conf /etc/myapp/app.conf    # /etc/myapp 기준으로 ../data/app.conf를 찾는다
```

다른 폴더에서 만들었는데 열리지 않는다면 대부분 이 문제다. 링크 위치와 상관없이 항상 같은 곳을 가리키게 하려면 절대 경로를 쓴다.

### 링크 이름이 이미 존재하는 폴더일 때 그 안에 링크가 생긴다

링크 이름으로 적은 경로가 이미 존재하는 폴더(또는 폴더를 가리키는 링크)면, `ln`은 그 폴더 **안에** 링크를 만든다. 배포 전환에서 `current`를 교체하려다 `current/v2` 같은 엉뚱한 링크가 생기는 사고가 이렇게 일어난다. 이름 자체를 대상으로 삼으려면 `-n`이나 `-T` 옵션이 필요하고, 앞에서 쓴 `mv -T` 방식이 이 문제를 함께 피한다.

### 링크를 지울 때 폴더처럼 다룬다

폴더를 가리키는 링크를 지울 때는 `rm 링크이름`이나 `unlink 링크이름`처럼 이름 뒤에 `/`를 붙이지 않고 지운다. 링크 이름 뒤에 `/`나 `/*`를 붙이면 링크가 아니라 가리키는 폴더 쪽을 다루게 된다. 특히 `rm -r 링크이름/*`는 링크가 가리키는 폴더 안의 내용을 지운다.

### 보안 때문에 막히는 경우를 만난다

공용 임시 폴더(`/tmp` 등)에서는 링크를 이용한 공격이 알려져 있어, 배포판이 이를 막는 커널 설정(`fs.protected_symlinks`, `fs.protected_hardlinks`)을 기본으로 켜 두는 경우가 많다. 그래서 다른 사용자 소유의 파일을 링크로 가리키려 하면 "Permission denied"가 나올 수 있다. 권한 오류가 나면 파일 권한뿐 아니라 이런 보호 설정도 한 번 떠올려 보면 된다.

|---|---|
| 아카이브 | 여러 파일과 폴더 구조를 하나로 묶은 보관 파일 |
| 묶기와 압축 | 묶기는 여러 자료를 하나로 모으는 일, 압축은 데이터 크기를 줄이는 일 |
| gzip | `tar -z`가 사용하는 압축 방식. 확장자는 보통 `.tar.gz` |
| 복원본 | 아카이브를 풀어서 얻은 사본. 원본과 별개의 대상 |
| diff | 두 파일이나 폴더의 내용 차이를 비교하는 명령 |
| inode | 파일의 속성과 데이터 위치를 관리하는 정보. 같은 파일시스템 안에서 번호로 구분 |
| 링크 수 | 하나의 파일에 연결된 이름의 개수. `ls -l`의 권한 뒤 숫자 |
| 심볼릭 링크 | 대상의 경로를 저장한 링크. 대상이 사라지면 깨진 링크가 됨 |
| 하드 링크 | 같은 파일에 붙은 또 하나의 이름. 같은 파일시스템 안의 일반 파일에 사용 |
| 깨진 링크 | 링크는 남아 있지만 가리키는 경로에 대상이 없는 상태 |
| 롤백 | 문제가 생겼을 때 이전 버전으로 되돌리는 일 |
| 증분 백업 | 이전 백업 이후 바뀐 부분만 새로 저장하는 백업 방식 |
