[지난 글](/2026/10/22/aws-s3-lifecycle/)까지 S3의 저장 방식과 데이터 관리 기능을 정리했다. 이번 글에서는 S3에 저장되는 데이터를 어떻게 보호하는지, 즉 **암호화**를 다룬다. 암호화는 "어디에서 어떤 주체가 암호화하는가"를 기준으로 세 단계로 나누면 헷갈리지 않는다.

## 암호화의 세 단계

![S3 암호화의 세 단계](/assets/images/aws-s3-encryption/s3_encryption_overview.png)

| 단계 | 암호화하는 시점·주체 | 방식 |
|---|---|---|
| **① 전송 중(In Transit)** | 클라이언트와 S3 사이를 이동하는 동안 | HTTPS(TLS). 업로드·다운로드 통신 구간의 암호화로, S3 자체의 암호화 기능은 아니다 |
| **② 저장 시(At Rest), 서버 사이드** | S3가 데이터를 디스크에 쓸 때 | SSE-S3, SSE-KMS, DSSE-KMS, SSE-C |
| **③ 클라이언트 사이드** | 클라이언트가 S3로 보내기 전에 | 사용자가 직접 암호화. S3는 암호화 여부를 알지 못한다 |

흔히 오해하는 부분이 서버 사이드 암호화가 무엇을 막아 주느냐다. 서버 사이드 암호화는 S3의 저장 매체가 통째로 유출되더라도 안의 데이터를 읽을 수 없게 해 준다. 하지만 인증된 정상 요청, 예를 들어 탈취한 계정 권한으로 객체를 받아 오는 경우에는 S3가 복호화해서 돌려준다. 공식 문서도 권한이 있는 요청이라면 암호화된 객체와 암호화되지 않은 객체를 접근하는 방식에 차이가 없다고 설명한다. 이런 상황까지 막으려면 업로드 전에 직접 암호화하는 클라이언트 사이드 암호화가 필요하다.

## 서버 사이드 암호화의 기본값: SSE-S3

별도 설정을 하지 않아도 S3는 데이터를 암호화해서 저장한다. 2023년 1월 5일부터 **모든 버킷의 기본 암호화는 SSE-S3**이고, 새로 업로드되는 모든 객체에 추가 비용과 성능 영향 없이 자동으로 적용된다. 이 기본 암호화는 끌 수 없다. 다만 이미 저장된 기존 객체가 자동으로 다시 암호화되지는 않으며, 필요하면 S3 배치 작업(Batch Operations)으로 복사해서 다시 암호화해야 한다. 한 객체에는 서로 다른 서버 사이드 방식을 동시에 적용할 수 없고, 아래 네 가지는 서로 배타적인 선택지다.

| 방식 | 키 관리 주체 | 특징 |
|---|---|---|
| **SSE-S3** | S3 | 기본값. 클라이언트가 신경 쓸 것이 없다 |
| **SSE-KMS** | AWS KMS | 키 단위 권한 분리와 감사 로그가 가능하다 |
| **DSSE-KMS** | AWS KMS + S3 | 서로 독립된 두 겹의 암호화 |
| **SSE-C** | 고객 | 요청마다 클라이언트가 키를 전달한다 |

### SSE-S3: S3가 알아서 한다

SSE-S3는 객체마다 고유한 키로 AES-256 암호화를 하고, 그 키 자체도 주기적으로 교체되는 루트 키로 다시 암호화한다. 클라이언트가 보내면 S3가 암호화해서 저장하고, 가져갈 때 복호화해서 돌려준다. 모든 일이 S3 안에서 일어나므로 클라이언트는 아무것도 느끼지 못한다.

### SSE-KMS: KMS로 키를 세밀하게 통제

SSE-KMS는 AWS KMS(Key Management Service)와 연동해서 암호화한다. SSE-S3와의 차이는 **키와 권한을 직접 통제하고 감사할 수 있다**는 점이다.

- **키 종류**: 키를 지정하지 않으면 S3가 계정 안에 만드는 AWS 관리형 키(`aws/s3`)를 쓰고, 직접 만드는 고객 관리형 키를 쓰면 생성·교체·비활성화와 접근 제어를 직접 할 수 있다. 대칭 키만 지원한다. 다른 계정과 공유해야 한다면 AWS 관리형 키는 쓸 수 없고 고객 관리형 키를 써야 한다.
- **권한 분리**: 업로드(`PutObject`)에는 해당 키에 대한 `kms:GenerateDataKey` 권한이, 다운로드에는 `kms:Decrypt` 권한이 필요하다. 그래서 업로드만 하는 주체와 다운로드만 하는 주체의 권한을 키 수준에서 나눌 수 있다. S3 권한이 있어도 `kms:Decrypt` 권한이 없으면 객체를 읽을 수 없다는 뜻이기도 하다. (멀티파트 업로드는 두 권한이 모두 필요하다.)
- **감사**: CloudTrail이 `GenerateDataKey`, `Decrypt` 같은 KMS 작업을 기록하므로 키 사용 이력을 추적할 수 있다.
- **같은 리전**: SSE-KMS를 쓰려면 KMS 키가 버킷과 같은 리전에 있어야 한다.
- **비용**: KMS 요금이 따로 붙는다. 요청이 많을 때 비용을 줄이는 **S3 버킷 키(Bucket Keys)** 를 켜면 S3에서 KMS로 가는 요청 수가 줄어 KMS 요청 비용을 최대 99% 줄일 수 있다. 버킷 키를 켜면 KMS 정책에서 객체 ARN 대신 버킷 ARN을 암호화 컨텍스트로 쓰게 되므로, 기존 IAM·키 정책을 먼저 확인해야 한다.

### DSSE-KMS: 두 겹의 서버 사이드 암호화

DSSE-KMS는 SSE-KMS와 비슷하지만, **서로 독립된 AES-256 암호화를 두 번** 적용한다. 첫 번째는 KMS가 만든 데이터 키로, 두 번째는 S3가 관리하는 별도의 키로 암호화한다. 한 겹이 뚫려도 다른 한 겹이 데이터를 보호하고, 다층 암호화를 요구하는 규제를 맞춰야 하는 경우에 쓴다. 두 겹이 모두 서버에서 일어나는 암호화이므로 클라이언트 사이드 암호화와는 다르다. 버킷 키는 지원하지 않고, SSE-KMS보다 지연 시간과 비용이 조금 더 든다.

### SSE-C: 고객이 키를 직접 제공

SSE-C는 클라이언트가 업로드할 때 암호화 키를 함께 보내면, S3가 그 키로 암호화한 뒤 **키는 저장하지 않는다.** 다운로드할 때도 같은 키를 다시 보내야 하고, 키를 잃어버리면 객체도 잃는다. 키와 객체의 대응 관계, 키 교체 같은 관리는 모두 고객의 몫이다. 공식 문서가 밝히는 제약은 다음과 같다.

- 요청은 반드시 HTTPS로 해야 한다. HTTP로 보내면 거부되고, 실수로 HTTP로 보낸 키는 노출된 것으로 보고 폐기해야 한다.
- S3 콘솔에서는 SSE-C로 업로드할 수 없다.
- AWS 관리형 서비스는 SSE-C 객체를 자체적으로 복호화할 수 없다.
- 버전 관리를 쓰면 버전마다 다른 키를 쓸 수 있어서, 어느 버전에 어느 키를 썼는지도 직접 추적해야 한다.

특히 **2026년 4월부터 SSE-C는 기본적으로 비활성화**되었다. 신규 범용 버킷은 처음부터 SSE-C가 막혀 있고, SSE-C로 암호화된 객체가 없는 계정의 기존 버킷도 마찬가지다. 막힌 상태에서 SSE-C로 쓰려는 요청은 403 `AccessDenied`로 거부된다. 꼭 필요하다면 버킷 암호화 설정(`PutBucketEncryption`)에서 `BlockedEncryptionTypes`를 `NONE`으로 바꿔 직접 허용해야 한다. AWS는 대부분의 워크로드에 SSE-KMS를 권장한다.

## 복제할 때 암호화는 어떻게 될까

강의에서는 KMS 키가 리전을 벗어나지 않아서 다른 리전으로 복제할 때 암호화 때문에 복제가 불가능해질 수 있다고 설명했다. 키가 리전 안에 묶여 있는 것은 맞지만, **SSE-KMS 객체도 리전 간 복제가 가능하다.** 다만 기본적으로는 복제 대상에서 제외되고, 직접 설정해야 한다.

- 복제 규칙에서 SSE-KMS 암호화 객체 복제를 활성화한다(`SseKmsEncryptedObjects`).
- 대상 리전에 만든 고객 관리형 대칭 KMS 키를 복제본 암호화 키로 지정한다(`ReplicaKmsKeyID`).
- 복제 역할에 원본 키의 `kms:Decrypt`, 대상 키의 `kms:Encrypt` 등 필요한 권한을 준다.

SSE-C 객체도 복제는 지원된다. 즉 "복제가 불가능하다"가 아니라 **대상 리전의 키와 권한을 따로 준비해야 한다**가 정확한 설명이다. 설정한 키가 잘못되어도 설정 요청은 성공으로 응답하고 복제만 실패하니 주의해야 한다.

## 클라이언트 사이드 암호화: 아무도 믿지 않을 때

클라이언트 사이드 암호화는 **S3로 보내기 전에 사용자가 직접 암호화**하는 방식이다. S3는 이미 암호화된 데이터를 받을 뿐 암호화에 관여하지 않고, 일반 객체와 구분하지도 못한다. 객체가 AWS를 포함한 제3자에게 노출되지 않는다는 점이 장점이다. AWS는 이를 위해 Amazon S3 Encryption Client를 제공하며, 클라이언트 사이드 암호화와 서버 사이드 암호화를 함께 쓸 수도 있다. 이 클라이언트는 버킷 키를 사용하지 않는다.

| 구분 | 서버 사이드 암호화 | 클라이언트 사이드 암호화 |
|---|---|---|
| 암호화하는 곳 | S3 서버 | 클라이언트 |
| S3가 평문을 보는가 | 요청 시점에 처리한다 | 평문을 보지 못한다 |
| 권한 있는 요청의 결과 | 복호화된 상태로 받는다 | 암호문 그대로 받는다 |
| 키 관리 | S3, KMS 또는 고객 | 고객 |

## 용어 정리

| 용어 | 설명 |
|---|---|
| **In Transit** | 클라이언트와 S3 사이 이동 중의 암호화. HTTPS(TLS)가 담당 |
| **At Rest** | S3에 저장된 상태의 암호화 |
| **SSE-S3** | S3가 키를 관리하는 서버 사이드 암호화. 2023년 1월부터 모든 버킷의 기본값 |
| **SSE-KMS** | KMS 키로 암호화. 키 단위 권한 분리와 CloudTrail 감사 가능 |
| **DSSE-KMS** | 독립된 두 겹의 AES-256을 적용하는 서버 사이드 암호화 |
| **SSE-C** | 요청마다 고객이 키를 제공. S3는 키를 저장하지 않으며 2026년 4월부터 기본 차단 |
| **S3 버킷 키(Bucket Keys)** | SSE-KMS의 KMS 호출을 줄여 비용을 낮추는 기능 |
| **클라이언트 사이드 암호화** | 업로드 전에 사용자가 직접 암호화. S3는 암호화 여부를 모름 |
