[지난 글](/2026/10/17/aws-s3-versioning-object-lock/)에서 버전 관리를 켜면 이전 버전이 계속 쌓여 비용이 늘 수 있다고 했다. 이번 글에서는 그 문제의 답이자, 스토리지 클래스를 직접 하나씩 바꾸지 않아도 되게 해 주는 **S3 수명 주기(Lifecycle)** 를 정리한다. 파일이 수십 개가 아니라 수만, 수억 개라면 사람이 일일이 관리할 수 없으니 규칙으로 일괄 처리한다.

## 수명 주기: 일정 기간이 지나면 객체의 상태를 바꾼다

수명 주기 규칙은 객체가 만들어진 뒤 정해진 기간이 지나면 자동으로 어떤 작업을 수행하게 하는 설정이다. 작업은 두 가지다.

- **전환(Transition)**: 객체를 다른 스토리지 클래스로 옮긴다. 예를 들어 30일 뒤 Standard-IA로, 90일 뒤 Glacier로 보낸다.
- **만료(Expiration)**: 객체를 삭제한다. 예를 들어 365일 뒤 지운다.

소셜 미디어 서비스에 올라온 이미지를 떠올리면 이해하기 쉽다. 처음에는 조회가 많지만 시간이 지나면 거의 보지 않게 된다. 이럴 때 일정 기간 뒤에 자주 쓰지 않는 데이터용 클래스로 옮기면 저장 비용을 줄일 수 있다.

![수명 주기 규칙 예시 타임라인](/assets/images/aws-s3-lifecycle/s3_lifecycle_timeline.png)

한 가지 알아둘 점은 수명 주기가 **소급 적용**된다는 것이다. 30일 뒤 만료하는 규칙을 만들면, 규칙을 만든 날부터 30일이 아니라 **객체가 처음 만들어진 날부터** 30일을 센다. 그래서 이미 30일이 지난 기존 객체들도 규칙을 만드는 순간 만료 대상이 된다.

## 전환 작업: 폭포수처럼 아래로만 흐른다

전환은 스토리지 클래스 간 **폭포수(Waterfall) 모델**을 따른다. 객체는 Standard 쪽에서 아카이브 쪽으로 내려가기만 하고, 다시 위로 올라가는 규칙은 만들 수 없다.

![스토리지 클래스 전환의 폭포수 모델](/assets/images/aws-s3-lifecycle/s3_lifecycle_waterfall.png)

공식 문서 기준으로 각 클래스에서 직접 전환할 수 있는 대상은 다음과 같다.

| 현재 클래스 | 전환 가능한 대상 |
|---|---|
| **Standard** | Standard-IA, Intelligent-Tiering, One Zone-IA, Glacier Instant, Glacier Flexible, Glacier Deep Archive |
| **Standard-IA** | Intelligent-Tiering, One Zone-IA, Glacier Instant, Glacier Flexible, Glacier Deep Archive |
| **Intelligent-Tiering** | 계층에 따라 다름. Frequent/Infrequent 계층은 One Zone-IA와 Glacier 계열 전부, Archive Instant Access는 Glacier Instant 이하 |
| **One Zone-IA** | Glacier Flexible, Glacier Deep Archive |
| **Glacier Instant** | Glacier Flexible, Glacier Deep Archive |
| **Glacier Flexible** | Glacier Deep Archive만 가능 |
| **Glacier Deep Archive** | 수명 주기로는 전환 불가. 복원한 뒤 복사해야 한다 |

표에서 보듯 One Zone-IA에서 Glacier Instant로 가는 것처럼, 아래에 있어도 직접 갈 수 없는 경로가 있다. 규칙을 만들기 전에 이 표를 확인하자.

전환에는 비용과 제약도 따른다.

- **작은 객체**: 2024년 9월부터 기본적으로 128KB보다 작은 객체는 어떤 클래스로도 전환되지 않는다. 작은 객체를 전환하려면 객체 크기 필터(`ObjectSizeGreaterThan` 등)로 대상을 직접 지정해야 한다.
- **Glacier 전환 비용**: Glacier Flexible Retrieval·Deep Archive로 객체를 전환할 때마다 전환 요청 1건의 비용이 든다. 객체마다 약 40KB의 메타데이터 오버헤드(8KB는 Standard 요금, 32KB는 아카이브 요금)도 붙어서, 작은 객체가 아주 많으면 비용이 절약분보다 클 수 있다.
- **최소 보관 기간**: 클래스를 옮기기 전 최소 보관 기간(Standard-IA/One Zone-IA 30일, Glacier Instant·Flexible 90일, Deep Archive 180일)이 끝나지 않았다면 남은 기간만큼 요금이 부과된다. 그래서 "Glacier Instant로 4일 뒤, Deep Archive로 20일 뒤" 같은 규칙 하나는 만들 수 없고, Deep Archive는 최소 94일 뒤에야 보낼 수 있다.
- **과금 시점**: Glacier 전환은 비동기로 처리되지만, 규칙 조건을 만족한 시점부터 목적지 클래스 요금이 적용된다. Intelligent-Tiering으로 가는 경우만 실제 전환 이후에 요금이 바뀐다.

## 만료 작업: 버전 관리 여부에 따라 동작이 다르다

만료는 버킷의 버전 관리 상태에 따라 다르게 동작한다.

| 상황 | 만료가 하는 일 |
|---|---|
| 버전 관리 없음 | 객체를 대기열에 올려 비동기로 영구 삭제한다 |
| 버전 관리 있음, 현재 버전이 일반 객체 | 삭제 마커를 추가한다. 기존 버전은 이전 버전이 된다 |
| 버전 관리 있음, 현재 버전이 삭제 마커(이전 버전이 남아 있음) | 아무 작업도 하지 않는다 |
| 버전 관리 일시 중지 | `null` 버전 ID의 삭제 마커를 만들어 같은 `null` 버전을 대체한다 |
| 이전 버전 | 이전 버전 만료(`NoncurrentVersionExpiration`) 규칙으로 영구 삭제한다. 복구할 수 없다 |

일반 만료 규칙은 현재 버전에만 적용되고 이전 버전에는 영향이 없다. 그래서 버전 관리 버킷에서는 이전 버전 만료 규칙을 별도로 둬야 쌓인 버전이 정리된다. 이전 버전이 모두 사라지고 삭제 마커만 남은 상태(만료된 삭제 마커)는 S3가 정리한다. 이 동작은 별도 규칙(`ExpiredObjectDeleteMarker`)으로도 지정할 수 있는데, 태그 필터와는 함께 쓸 수 없다.

만료 시점과 비용에 관해 알아둘 점이 있다.

- **삭제 지연**: 만료 날짜가 되어도 실제 삭제까지 지연이 있을 수 있다. S3는 만료·전환 시점을 다음 날 자정(UTC)으로 올림해서 처리한다. 삭제 시점에 맞춰 다른 작업을 연결해 둔다면 이 점을 감안해야 한다.
- **비용**: 만료된 객체에 대해서는 만료 처리 비용도, 만료 이후의 저장 비용도 청구되지 않는다. 예를 들어 5월 30일에 지워질 객체가 6월 2일에야 지워졌어도 그 이틀치는 내지 않는다.
- **만료 예정 확인**: `HeadObject`나 `GetObject` 응답으로 객체의 만료 예정 시점을 확인할 수 있다.
- **하루 한 번의 작업**: 객체는 하루에 하나의 수명 주기 작업만 적용된다. 여러 규칙이 겹치면 영구 삭제가 전환보다, 전환이 삭제 마커 생성보다 우선한다.
- **제외 대상**: Object Lock이 걸린 이전 버전, 그리고 복제 상태가 `Pending`·`Failed`인 객체에는 작업이 적용되지 않는다. 또 버킷 정책으로 수명 주기 삭제·전환을 막을 수는 없다.
- **태그 필터**: 태그는 매일 평가해 대기열에 올린 뒤 실행 시점에 다시 확인한다. 그 사이 태그가 사라지면 만료는 진행되지 않는다.
- **MFA Delete와 비호환**: MFA Delete는 수명 주기 설정과 함께 쓸 수 없다.

## 멀티파트 업로드 정리: 실패한 조각도 비용이 나온다

앞서 멀티파트 업로드를 배울 때, 업로드가 실패하면 완성되지 못한 조각이 남아 용량을 차지한다고 했다. 이 조각은 눈에 잘 띄지 않지만 저장 비용이 계속 나온다. 수명 주기에는 **완료되지 않은 멀티파트 업로드를 일정 기간 뒤 삭제**하는 옵션이 있다. 멀티파트 업로드를 쓰는 버킷이라면 이 규칙을 반드시 함께 설정해 두는 것이 좋다. 이 규칙에는 태그 기반 필터를 쓸 수 없고, 접두사로 대상을 지정한다.

## 조건과 필터: 어떤 객체에, 언제 적용할까

**시간 조건**은 "생성 후 N일"처럼 일수(`Days`)로 지정하거나, 특정 날짜(`Date`)로 지정한다. 한 규칙에서 `Days`와 `Date`를 함께 쓸 수는 없다. 규칙은 이미 있는 객체와 앞으로 올릴 객체 모두에 적용된다.

**필터**는 규칙의 대상을 좁힌다. 필터는 하나만 지정하거나, 여러 개를 쓸 때는 `And`로 묶어 모두 만족하는 객체에만 적용한다.

| 필터 | 예시 |
|---|---|
| **접두사(Prefix)** | `logs/`, `logs/production/`, `images/thumbnails/` 아래의 모든 객체 |
| **태그** | `condition=delete` 태그가 붙은 객체. 여러 태그를 `And`로 조합 가능 |
| **객체 크기** | 1MB 초과·3MB 미만처럼 최소·최대 크기 지정 (지정한 값은 범위에서 제외) |

필터는 조합할 수 있다. "`images/` 접두사에서 5MB보다 큰 파일만 삭제"처럼 구체적으로 지정한다. 태그를 활용하면 평소에는 그대로 두고, 태그를 붙인 객체에만 규칙이 반응하게 만들 수도 있다.

## 콘솔에서 보면: 관리 탭의 수명 주기 규칙

버킷에 들어가 **관리(Management)** 탭을 열면 가장 먼저 `수명 주기 규칙`이 보이고, 여기서 규칙을 만든다. 설정 흐름은 이렇다.

1. 규칙 이름을 정하고 적용 범위를 고른다. 버킷 전체에 적용하거나, 접두사·태그·객체 크기 필터로 범위를 제한한다.
2. 규칙 작업을 고른다. 선택지는 현재 버전 객체의 스토리지 클래스 전환, 이전 버전 객체의 전환, 현재 버전 객체 만료, 이전 버전 객체 영구 삭제, 만료된 삭제 마커·완료되지 않은 멀티파트 업로드 삭제다.
3. 이전 버전 영구 삭제에서는 며칠 뒤 지울지와 함께 **최신 몇 개 버전을 남길지**(1~100개)를 정할 수 있다. 예를 들어 "이전 버전은 최신 5개만 보관"하는 식으로 버전이 무한히 쌓이는 것을 막는다. 이때 며칠이 지났는지와 보관 개수를 **모두** 초과한 버전만 삭제된다.
4. 현재 버전이 만료되는 날짜를 지정하면, 버전 관리가 없는 버킷에서는 객체가 삭제되고 버전 관리가 있는 버킷에서는 삭제 마커가 얹힌다.

## 실전 시나리오 예시

| 대상 | 규칙 |
|---|---|
| 로그 버킷 (`logs/`) | 30일 후 Standard-IA, 90일 후 Glacier Flexible, 365일 후 만료 |
| 버전 관리 버킷 | 이전 버전은 최신 5개만 유지, 30일 지난 이전 버전은 영구 삭제 |
| 멀티파트를 쓰는 버킷 | 시작 후 7일 지난 미완료 업로드 삭제 |
| 임시 파일 (`condition=delete` 태그) | 생성 후 3일 뒤 만료 |

규칙을 걸기 전에는 `ListObjectsV2`, `ListObjectVersions`, S3 Inventory 등으로 어떤 객체가 어떻게 전환·만료될지 미리 확인하는 것이 안전하다. 객체가 아주 작고 많다면 전환 비용이 절약분보다 클 수 있다는 점도 함께 따져 보자.

## 용어 정리

| 용어 | 설명 |
|---|---|
| **수명 주기(Lifecycle) 규칙** | 일정 기간이 지난 객체에 전환·만료 작업을 자동 수행하는 버킷 설정 |
| **전환(Transition)** | 객체를 다른 스토리지 클래스로 옮기는 작업 |
| **만료(Expiration)** | 객체를 삭제하는 작업. 버전 관리 버킷에서는 삭제 마커 추가 |
| **폭포수 모델** | 스토리지 클래스 전환이 아래 방향으로만 가능한 구조 |
| **소급 적용** | 기존 객체에도 규칙이 적용되며, 기간은 객체 생성일부터 계산 |
| **이전 버전(Noncurrent Version)** | 버전 관리 버킷에서 최신이 아닌 버전. 별도 규칙으로 전환·삭제 가능 |
| **만료된 삭제 마커** | 이전 버전이 모두 사라지고 삭제 마커만 남은 상태. S3가 정리한다 |
| **Prefix / 태그 / 객체 크기** | 규칙 적용 대상을 좁히는 필터 조건 |
| **미완료 멀티파트 업로드 삭제** | 실패한 업로드 조각을 정리해 불필요한 비용을 막는 옵션 |
