[지난 글](/2026/09/17/aws-security-group-source/)까지 Security Group을 다뤘다. 이번 글에서는 VPC의 또 다른 보안 계층인 **NACL(Network Access Control List)**을 정리하고, 지금까지 미뤄뒀던 Security Group과의 전체 비교까지 마무리한다.

## NACL: Subnet 단위 방화벽, Security Group과 다른 점

NACL은 하나 이상의 Subnet을 드나드는 트래픽을 제어하는 VPC의 선택적 보안 계층이다. Security Group과 같은 방화벽 역할이지만 적용 단위가 다르다. Security Group은 ENI(사실상 인스턴스) 단위였는데, NACL은 **Subnet 단위**다. 그래서 인스턴스별로 세밀하게 제어할 수는 없고, Subnet 전체에 적용된다.

관계도 반대 방향이다. 하나의 EC2에는 Security Group을 여러 개 붙일 수 있었지만, **하나의 Subnet은 NACL을 딱 하나만 연동할 수 있다.** 대신 **하나의 NACL은 여러 Subnet에 동시에 연동될 수 있다.** 즉 NACL 기준으로는 1대다, Subnet 기준으로는 1대1인 셈이다.

가장 중요한 차이는 두 가지다. Security Group은 Allow만 가능했지만, NACL은 **포트와 IP를 명시적으로 Deny할 수 있다.** 특정 IP를 차단하고 싶을 때 Security Group으로는 불가능했던 걸 NACL로 할 수 있는 이유다. 그리고 Security Group은 Stateful이었지만, NACL은 **Stateless**다. 들어오는 트래픽과 나가는 트래픽을 구분해서 각각 체크한다.

| 구분 | Security Group | NACL |
|---|---|---|
| 적용 단위 | ENI (사실상 인스턴스) | Subnet |
| 인스턴스-보안 관계 | 인스턴스 1개에 SG 여러 개 가능 | Subnet 1개에 NACL 1개만 |
| Deny 설정 | 불가능 (Allow만) | 가능 |
| 상태 추적 | Stateful | Stateless |
| 규칙 평가 | 관련된 규칙 전부 평가 | 번호 순서대로 평가, 매칭되면 즉시 중단 |
| 적용 범위 | 인스턴스 트래픽 전체 | Subnet 경계를 드나드는 트래픽만 |

## Stateless라는 것의 의미: 아웃바운드도 항상 체크한다

[지난 Security Group 글](/2026/09/16/aws-security-group/)에서 Stateful/Stateless와 Ephemeral Port(임시 포트) 개념을 다뤘다. NACL을 실제로 쓰려면 이 개념이 그대로 발목을 잡는다.

클라이언트가 서버에 요청을 보낼 때는 서버의 Well-known Port(예: HTTP 80)로 보내고, 자신은 그 순간 비어 있는 포트 중 하나를 무작위로 골라 쓴다. 이게 Ephemeral Port다. 서버가 응답을 보낼 때는 정확히 그 Ephemeral Port로 돌려보낸다.

Security Group은 Stateful이라 인바운드로 들어온 요청에 대한 응답은 아웃바운드 규칙 없이도 자동으로 나간다. 하지만 NACL은 Stateless라 인바운드에서 80번을 허용해도, 그 응답이 나가려면 **아웃바운드에 Ephemeral Port 범위가 따로 허용되어 있어야 한다.** 문제는 이 Ephemeral Port가 매번 무작위로 바뀐다는 점이다. 그래서 포트 하나만 여는 게 아니라 범위 전체를 열어둬야 한다.

이 범위는 운영체제마다 다르다.

| OS | Ephemeral Port 범위 |
|---|---|
| Linux | 32768–60999 |
| Windows (구버전) | 1025–5000 |
| Windows (Vista 이후) | 49152–65535 |

클라이언트가 어떤 OS를 쓸지 알 수 없기 때문에, 실무에서는 보통 이 범위를 넉넉하게 포괄하는 **1025–65535**를 아웃바운드로 열어두는 경우가 많다. NACL에서 발생하는 통신 문제의 상당수는 이 Ephemeral Port 범위를 안 열어놔서 생긴다.

## NACL 규칙: 번호가 낮은 것부터 평가되고, 매칭되면 즉시 멈춘다

NACL 규칙은 규칙 번호, 유형(SSH 22, DNS 53 등), 프로토콜(TCP/UDP 등), 포트 범위, Source, Allow/Deny로 구성된다. 여기서 가장 중요한 건 **규칙 번호가 평가 순서를 결정한다**는 점이다. 낮은 번호부터 차례로 평가하다가 조건이 매칭되는 규칙을 만나면 그 즉시 적용하고 평가를 멈춘다. 뒤에 더 구체적인 규칙이 있어도 소용없다.

![NACL 규칙 순서에 따라 차단 여부가 달라지는 예시](/assets/images/aws-nacl/nacl_rule_order.png)

`112.12.35.4`라는 특정 IP를 차단하고 싶다고 해보자. 규칙 100번에 "TCP 80, 모든 소스, Allow"를 넣고 규칙 200번에 "TCP 80, `112.12.35.4/32`, Deny"를 넣으면 어떻게 될까? 차단되지 않는다. 100번이 먼저 평가되는데 이 IP도 결국 "모든 소스"에 포함되므로 100번에서 매칭되어 즉시 Allow로 끝나버리고, 200번까지 도달하지도 못한다.

제대로 차단하려면 차단 규칙을 더 낮은 번호(예: 50번)에 둬서 넓은 범위의 Allow 규칙보다 먼저 평가되게 해야 한다.

이런 이유로 AWS는 규칙 번호를 **100단위로 띄워서** 만들 것을 권장한다. 규칙을 1, 2 이렇게 촘촘하게 만들어두면, 나중에 그 사이에 규칙을 끼워 넣고 싶을 때 뒤에 있는 규칙 번호를 전부 밀어야 한다. 100, 200 단위로 여유를 둬두면 50, 150처럼 중간에 끼워 넣을 자리가 넉넉하다.

## NACL은 Subnet 경계에서만 동작한다

NACL은 Subnet을 드나드는 트래픽에만 적용된다. 같은 Subnet 안에 있는 EC2끼리 서로 통신하는 트래픽에는 전혀 관여하지 않는다. Subnet 경계를 넘나드는 트래픽이 아니기 때문이다.

## 멀티티어 아키텍처에서 조심해야 할 점

여러 Subnet이 하나의 NACL을 공유하는 멀티티어 구조에서는 Ephemeral Port 처리가 한층 복잡해진다.

![멀티티어에서 NACL을 공유할 때 열어야 하는 포트 방향](/assets/images/aws-nacl/nacl_multitier.png)

외부 클라이언트가 웹 서버(EC2)에 접속해서, EC2가 DB를 조회한 뒤 응답을 돌려주는 흐름을 생각해보자. 클라이언트 → EC2 구간에서는 EC2가 서버 역할이라 인바운드 80번만 허용하면 되고, 응답은 아웃바운드 Ephemeral 범위를 열어야 한다. 여기까지는 지금까지 설명한 것과 같다.

문제는 EC2 → DB 구간이다. 이 구간에서는 EC2가 반대로 **클라이언트 역할**이다. EC2는 자신의 Ephemeral Port를 사용해서 DB의 3306번(Well-known)으로 요청을 보낸다. 그리고 DB가 응답을 보낼 때는 EC2의 그 Ephemeral Port로 돌려보낸다. 즉 이 응답은 EC2 입장에서 **인바운드로 들어오는 트래픽**이고, 목적지 포트는 EC2의 Ephemeral Port다.

그래서 이 NACL은 "나가는 응답을 위한 Outbound Ephemeral"뿐 아니라, "DB로부터 받는 응답을 위한 Inbound Ephemeral"도 함께 열어둬야 한다. 한 EC2가 어떤 트래픽에서는 서버, 다른 트래픽에서는 클라이언트 역할을 동시에 하기 때문에 생기는 문제다. NACL이 여러 Subnet(예: Web tier, DB tier)을 걸쳐 공유될 때는 이 점을 특히 꼼꼼히 따져봐야 한다.

## 기본 원칙: Security Group을 먼저 쓰고, NACL은 보조 수단으로

NACL은 강력하지만 Stateless라는 특성 때문에 다루기가 까다롭다. 일반적으로는 가능한 한 Security Group으로 보안을 처리하고, Security Group으로 할 수 없는 것(예: 특정 IP 명시적 차단)만 NACL로 보완하는 방식을 권장한다.

## 기본 VPC의 NACL vs 직접 만든 NACL

VPC를 생성하면 기본으로 NACL이 하나 딸려온다. 이 기본 NACL은 **모든 트래픽이 Allow로 되어 있어서** 별도로 신경 쓰지 않아도 기존처럼 동작한다. 반면 NACL을 직접 새로 만들면 **기본값이 모든 트래픽 Deny**다. 이 차이를 모르고 NACL을 새로 만들었다가 아무 트래픽도 안 통해서 당황하는 경우가 흔하다.

## 실습에서 확인한 것: 규칙 순서와 Stateless의 함정

기본 NACL(규칙 100번에 전체 Allow)에 SSH를 차단하는 규칙을 200번으로 추가하면, 이론대로 SSH가 여전히 연결된다. 100번에서 이미 Allow로 매칭되어 끝나버리기 때문이다. 이 규칙을 50번으로 옮기면 그제서야 SSH가 제대로 차단된다.

Security Group과의 차이도 직접 비교해볼 만하다. Security Group에서 아웃바운드 규칙을 전부 지워도 이미 맺어진 웹 트래픽은 계속 잘 받아진다 — Stateful이라 인바운드에 대한 응답은 자동으로 나가기 때문이다. 하지만 NACL에서 아웃바운드를 전부 Deny로 바꾸면, 요청은 들어오는데 응답이 나가지 못해 그 자리에서 타임아웃이 난다. Stateless는 들어오는 것과 나가는 것을 정말로 각각 따로 본다는 걸 실습으로 확인할 수 있다.

## 용어 정리

| 용어 | 설명 |
|---|---|
| **NACL** | Subnet 단위로 동작하는 Stateless 방화벽. Allow·Deny 모두 가능 |
| **규칙 번호** | NACL 규칙의 평가 순서. 낮은 번호부터 평가하며 매칭되면 즉시 중단 |
| **100단위 규칙 번호** | 나중에 규칙을 끼워 넣을 여유를 남기기 위한 관례 |
| **Ephemeral Port** | 클라이언트가 통신마다 무작위로 고르는 임시 포트. NACL에서는 범위로 열어야 함 |
| **기본 NACL** | VPC 생성 시 자동으로 딸려오는 NACL. 기본값이 전체 Allow |
| **직접 생성한 NACL** | 기본값이 전체 Deny |

이걸로 Security Group과 NACL을 한 세트로 정리했다. 다음 글에서는 이번 챕터에서 계속 언급됐던 VPC 전체 아키텍처(ALB, Auto Scaling Group 포함)를 직접 구성해보는 내용을 다룬다.
