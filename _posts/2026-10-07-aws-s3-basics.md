[지난 글](/2026/10/04/aws-s3-intro/)에서 S3가 왜 필요한지, 객체 스토리지가 무엇인지 큰 그림을 잡았다. 이번 글에서는 S3를 실제로 쓰기 위해 알아야 할 기본기 — 버킷과 객체의 구조, 내구성과 가용성, 기본 보안, 비용 — 를 정리하고, EC2가 S3에서 파일을 내려받는 간단한 실습까지 이어간다.

## S3: 글로벌 서비스처럼 보이지만 데이터는 리전에 저장된다

S3는 콘솔에서 리전을 바꿔도 같은 버킷 목록이 보이기 때문에 글로벌 서비스처럼 느껴진다. 하지만 **버킷은 특정 리전에 만들어지고, 데이터도 그 리전 안에 저장된다.** 데이터를 특정 국가 안에 두어야 하는 규제나 정책이 있을 때 이 점이 중요하다. 서울 리전에 만든 버킷의 데이터는 사용자가 따로 복제를 설정하지 않는 한 서울 리전 밖으로 나가지 않는다.

또 S3는 EBS나 EFS 같은 블록·파일 스토리지와 달리 **객체 스토리지**다. 서버에 디스크처럼 붙여서 쓰는 게 아니라, HTTP API로 객체를 올리고 내려받는 방식이다. 전체 용량에는 사실상 제한이 없고, 쓴 만큼만 비용을 낸다.

## 버킷과 객체: 리전 안의 버킷, 버킷 안의 객체

S3의 구조는 단순하다. 리전 안에 **버킷(Bucket)** 이라는 컨테이너를 만들고, 그 안에 **객체(Object)** 를 저장한다.

![S3 버킷과 객체의 구조](/assets/images/aws-s3-basics/s3_bucket_object.png)

버킷 이름은 기본적으로 전 세계에서 유일해야 한다. 그래서 `my-bucket` 같은 이름은 이미 누군가 쓰고 있을 가능성이 높고, 실습에서는 `demo-my-s3-bucket-<계정ID>`처럼 계정 ID를 붙여 충돌을 피하곤 한다. 참고로 2026년 3월부터 버킷 이름에 계정 ID와 리전을 붙여 계정 단위로 이름 공간을 분리하는 **Account Regional Namespace** 옵션이 생겼다(`<이름>-<계정ID>-<리전>-an` 형태). 선택 사항이고 기본은 여전히 전역 고유 이름이다.

객체 하나는 다음 요소로 구성된다.

| 구성 요소 | 설명 |
|---|---|
| **소유자(Owner)** | 객체를 소유한 계정 |
| **키(Key)** | 객체의 이름(경로). 객체를 찾는 기준 |
| **값(Value)** | 실제 파일 데이터. 비어 있어도 되므로 0바이트 객체도 가능 |
| **버전 ID(Version ID)** | 버저닝을 켰을 때 같은 키의 버전을 구분 |
| **메타데이터(Metadata)** | 콘텐츠 타입, 생성 목적 등 부가 정보 |
| **ACL** | 객체 단위 접근 권한. 요즘은 거의 쓰지 않는다 |

객체 하나의 크기는 0바이트부터 최대 5TB까지다. 다만 한 번의 PUT 요청으로 올릴 수 있는 크기는 최대 5GB라서, 그보다 큰 파일은 **멀티파트 업로드**로 쪼개 올려야 한다(보통 100MB를 넘으면 멀티파트를 권장한다).

## 내구성과 가용성: 비슷해 보이지만 다른 숫자

S3 Standard의 **내구성(Durability)** 은 99.999999999%, 이른바 "11 나인"이다. 내구성은 저장한 데이터가 **사라지지 않을 확률**이다. AWS 문서의 예시로는 객체 1,000만 개를 저장했을 때 평균적으로 약 1만 년에 한 개 정도 유실될 수 있는 수준이다. 여러 AZ에 데이터를 자동으로 복제해 두기 때문에 가능한 숫자다.

반면 **가용성(Availability)** 은 필요할 때 **접근할 수 있는 시간의 비율**이다. S3 Standard는 설계 목표가 99.99%이고, AWS가 약속하는 SLA는 99.9%다. 데이터가 사라지지는 않았지만 잠시 읽을 수 없는 상황은 가용성의 영역이다. 둘을 혼동하기 쉬운데, 내구성은 "잃어버리지 않는가", 가용성은 "지금 꺼낼 수 있는가"로 구분하면 된다.

## 보안: 기본은 전부 비공개

S3 버킷과 객체는 **기본적으로 비공개**다. 만든 직후에는 소유자와 권한을 부여받은 주체만 접근할 수 있다. 외부에 공개하려면 사용자가 명시적으로 열어야 하고, 실수로 열리는 것을 막기 위해 **퍼블릭 액세스 차단(Block Public Access)** 설정이 기본으로 켜져 있다.

접근 제어 방법은 크게 두 가지다.

- **버킷 정책(Bucket Policy)**: 버킷 단위로 JSON 정책을 붙이는 방식. 현재 권장되는 방법이다.
- **ACL**: 객체 단위로 권한을 주는 구식 방식. 신규 버킷에서는 기본적으로 비활성화되어 있고 점점 사용하지 않는 추세다.

여기에 몇 가지 보호 장치를 더할 수 있다.

- **버저닝(Versioning)**: 같은 키로 덮어쓰거나 삭제해도 이전 버전을 복구할 수 있다.
- **MFA Delete**: 버전을 영구 삭제하거나 버저닝 상태를 바꿀 때 MFA 인증을 요구한다.
- **액세스 로그**: 누가 어떤 객체에 접근했는지 기록한다.

강의에서는 서버 액세스 로그를 다른 계정의 버킷에 저장할 수 있다고 설명했지만, 이 부분은 정확하지 않다. **S3 서버 액세스 로그의 대상 버킷은 원본 버킷과 같은 계정, 같은 리전에 있어야 한다.** 계정을 넘나드는 로깅이 필요하다면 CloudTrail 데이터 이벤트나 CloudWatch Logs 같은 다른 경로를 쓰는 것이 맞다.

## 비용: 저장량, 요청 수, 데이터 전송량

S3 비용은 크게 세 가지로 나뉜다. 아래는 미국 동부(버지니아 북부) 기준 S3 Standard 가격이며, 리전과 시점에 따라 달라지므로 실제로는 [공식 요금표](https://aws.amazon.com/s3/pricing/)에서 확인해야 한다(확인일: 2026년 10월).

| 항목 | 대략적인 가격 |
|---|---|
| 저장 용량 | GB당 월 $0.023 (처음 50TB까지) |
| PUT / COPY / POST / LIST 요청 | 1,000건당 $0.005 |
| GET 요청 | 1,000건당 $0.0004 |
| 인터넷으로 나가는 데이터 전송 | GB당 $0.09 (월 100GB까지는 계정 전체 기준 무료) |

데이터를 **올리는 것(인바운드)은 무료**이고, **인터넷으로 내려받는 것(아웃바운드)** 에 비용이 붙는다. 읽기보다 쓰기·목록 조회 요청이 훨씬 비싸다는 점도 기억해 두면 좋다. 작은 파일을 엄청나게 많이 올리는 구조라면 저장 용량보다 요청 비용이 더 크게 나올 수 있다.

## 실습: EC2가 시작될 때 S3에서 index.html 가져오기

이제 S3와 EC2를 연결해 본다. 시나리오는 간단하다. S3에 `index.html`을 올려두고, EC2가 시작될 때 이 파일을 내려받아 웹 서버로 보여준다.

![EC2가 S3에서 index.html을 가져오는 흐름](/assets/images/aws-s3-basics/s3_ec2_demo_flow.png)

**1. 버킷 만들고 파일 올리기**

서울 리전에서 버킷을 만든다. 이름은 계정 ID를 붙여 `demo-my-s3-bucket-<계정ID>` 형태로 짓고, 나머지 설정은 기본값(퍼블릭 액세스 차단 켜짐)으로 둔다. "Hello World"가 적힌 `index.html`을 업로드한다.

**2. EC2용 IAM 역할 만들기**

EC2가 S3에 접근하려면 권한이 필요하다. 서버에 액세스 키를 저장하는 대신 **IAM 역할**을 만들어 인스턴스에 붙이는 것이 정석이다. 역할이 인스턴스 프로파일 형태로 EC2에 연결되면, 인스턴스는 임시 자격 증명을 자동으로 받는다. 실습에서는 편의상 `AmazonS3FullAccess` 정책을 붙이지만, 실무에서는 **해당 버킷의 필요한 작업만 허용하는 최소 권한 정책**을 직접 만들어 쓰는 것이 맞다.

**3. EC2 인스턴스 시작하기**

인스턴스 이름을 `demo-s3-test` 등으로 지정하고, 위에서 만든 IAM 역할을 인스턴스 프로파일로 연결한다. 보안 그룹에서는 HTTP(80)를 허용한다. 그리고 **User Data**에 웹 서버를 설치·실행하고, AWS CLI로 버킷의 `index.html`을 웹 루트로 복사하는 스크립트를 넣는다. User Data는 인스턴스가 처음 부팅될 때 한 번 실행되는 스크립트다.

**4. 확인하기**

인스턴스가 실행되면 Public DNS로 접속해 본다. 브라우저에 Hello World가 보이면 성공이다. 이렇게 하면 서버를 새로 띄울 때마다 S3에 올려둔 파일을 자동으로 가져올 수 있어서, 설정 파일이나 정적 리소스를 배포하는 방식으로 실전에서도 자주 쓰인다.

**5. 정리하기**

실습이 끝나면 비용이 발생하지 않도록 리소스를 지운다. 버킷은 안에 객체가 남아 있으면 삭제할 수 없으므로, 먼저 **버킷을 비운 다음**(콘솔에서 `영구 삭제`를 입력해 확인) 버킷 이름을 직접 입력해 삭제한다. EC2 인스턴스도 함께 종료한다.

## 용어 정리

| 용어 | 설명 |
|---|---|
| **버킷(Bucket)** | 객체를 담는 컨테이너. 특정 리전에 생성되며 이름은 전역 고유 |
| **객체(Object)** | S3에 저장되는 데이터 단위. 키·값·메타데이터 등으로 구성, 0B~5TB |
| **키(Key)** | 객체의 이름(경로) |
| **멀티파트 업로드** | 큰 객체를 여러 조각으로 나눠 올리는 방식. 단일 PUT은 최대 5GB |
| **내구성(Durability)** | 데이터가 유실되지 않을 확률. S3 Standard 99.999999999% |
| **가용성(Availability)** | 필요할 때 접근 가능한 비율. S3 Standard 설계 99.99%, SLA 99.9% |
| **버킷 정책** | 버킷 단위로 접근 권한을 정의하는 JSON 정책 |
| **Block Public Access** | 버킷·객체의 퍼블릭 노출을 막는 안전장치. 기본 켜짐 |
| **MFA Delete** | 영구 삭제 등 민감한 작업에 MFA 인증을 요구하는 기능 |
| **IAM 역할 / 인스턴스 프로파일** | 액세스 키 없이 EC2에 AWS 권한을 부여하는 방식 |
| **User Data** | 인스턴스 최초 부팅 시 실행되는 초기화 스크립트 |

다음 글에서는 S3의 스토리지 클래스와 수명 주기 관리 등, 비용을 줄이면서 데이터를 보관하는 방법을 이어서 다룬다.
