[지난 글](/2026/10/25/aws-s3-encryption/)에서는 S3 객체를 전송 중, 저장 시, 클라이언트 사이드의 세 단계에서 어떻게 보호하는지 살펴봤다. 이번 글은 S3의 또 다른 쓰임새인 **정적 웹 호스팅**이다. 서버를 띄우지 않고 버킷만으로 웹사이트를 서비스하는 기능인데, 먼저 "정적"이 무엇인지부터 정리한 뒤 동작 방식, 제약, 도메인과 HTTPS 연결까지 이어간다.

## 개념: 정적 콘텐츠와 동적 콘텐츠

**정적 콘텐츠(Static Content)** 는 서버에 저장된 파일이 모든 사용자에게 똑같이 전달되는 콘텐츠다. 요청마다 서버가 계산할 일이 없으므로 한 번 받아 둔 것을 그대로 **캐싱**해서 보여줘도 된다. HTML, CSS, JavaScript 파일과 이미지, 미리 작성된 글이나 뉴스 본문이 대표적이다. 회사 로고나 포털 대문 이미지처럼 누가 요청해도 같은 결과가 나오면 정적이다.

**동적 콘텐츠(Dynamic Content)** 는 시간, 사용자, 입력에 따라 내용이 달라지는 콘텐츠다. 요청이 올 때마다 서버가 내용을 구성해서 내려줘야 하고, 이 일을 PHP, JSP, ASP.NET 같은 서버 측 언어나 프레임워크가 맡는다. 로그인 후에만 보이는 화면, 게시판 글 목록, 실시간으로 달리는 댓글, 게임이 여기에 속한다.

같은 게시판 안에서도 두 종류가 섞여 있다는 점이 헷갈리기 쉽다. 이미 작성된 글 본문이나 이미지는 정적이지만, **글 목록이 어떻게 구성되는지, 새 댓글이 달렸는지**는 동적이다. 만약 게시판 목록을 하루 동안 캐싱한다면 하루 동안 새 글이 보이지 않을 것이고, 그러면 게시판의 의미가 사라진다. 그래서 동적인 부분은 접속할 때마다 서버에 물어봐야 한다.

| 구분 | 정적 콘텐츠 | 동적 콘텐츠 |
|---|---|---|
| 응답 내용 | 모든 사용자에게 동일 | 시간·사용자·입력에 따라 변경 |
| 서버 연산 | 필요 없음 | 요청마다 필요 |
| 캐싱 | 가능 | 제한적 |
| 구성 | HTML, JavaScript, 이미지 등 파일 | PHP, JSP, ASP.NET 등 서버 코드와 DB |
| 예시 | 회사 소개, 홍보·사전예약 페이지 | 로그인 화면, 게시판 목록, 댓글 |

이 구분은 뒤에서 CloudFront를 다룰 때 다시 중요해지고, 지금은 "S3가 서빙할 수 있는 것은 정적 콘텐츠뿐"이라는 점만 기억하면 된다.

## 개념: S3 정적 웹 호스팅

S3 정적 웹 호스팅은 버킷에 올린 HTML, CSS, JavaScript, 이미지 같은 파일을 웹사이트로 서비스하는 기능이다. EC2나 별도의 웹 서버를 프로비저닝하지 않고 파일만 올리면 되기 때문에, 대규모 접속이 예상되는 사전예약 페이지, 홍보 페이지, 회사 소개 사이트 같은 곳에 잘 맞는다. 이 블로그처럼 정적 사이트 생성기로 만든 결과물을 올리는 용도로도 쓴다.

장점은 세 가지로 정리된다.

- **고가용성과 내구성:** S3 자체가 여러 AZ에 데이터를 저장하는 구조라서, ALB나 Auto Scaling으로 직접 가용성을 설계할 필요가 없다. 내구성은 [지난 S3 기초 글](/2026/10/07/aws-s3-basics/)에서 다룬 11 나인(99.999999999%)이다.
- **서버리스, 쓴 만큼만 과금:** EC2는 사용자가 없어도 인스턴스가 떠 있는 동안 비용이 나가지만, S3는 저장한 용량과 실제로 처리한 요청 수만큼만 비용을 낸다.
- **쉬운 배포와 수정:** 서버에 접속할 필요 없이 파일을 업로드하면 곧바로 반영된다.

## 개념: 웹사이트 엔드포인트와 REST 엔드포인트

같은 버킷이라도 접근하는 주소가 두 종류다. 평소 SDK나 CLI가 쓰는 **REST API 엔드포인트**와, 정적 호스팅을 켜면 추가로 생기는 **웹사이트 엔드포인트**다. 둘은 동작이 꽤 다르다.

![S3 정적 웹 호스팅: 직접 접속과 CloudFront를 앞에 둔 구성](/assets/images/aws-s3-static-hosting/s3_static_hosting_overview.png)

| 항목 | 웹사이트 엔드포인트 | REST API 엔드포인트 |
|---|---|---|
| 주소 형식 | `bucket.s3-website-<리전>.amazonaws.com` 또는 `bucket.s3-website.<리전>.amazonaws.com` | `bucket.s3.<리전>.amazonaws.com` |
| 접근 제어 | **공개 읽기** 콘텐츠만 지원 | 공개·비공개 모두 지원 |
| 지원 요청 | 객체에 대한 `GET`, `HEAD`만 | 모든 버킷·객체 작업 |
| 루트(`/`) 요청 | 인덱스 문서 반환 | 객체 키 목록 반환 |
| 오류 응답 | HTML 문서 | XML |
| 리다이렉트 | 객체·버킷 단위 지원 | 해당 없음 |
| SSL/TLS | **지원하지 않음 (HTTP만)** | 지원 |

리전에 따라 주소의 `s3-website` 뒤가 점(.)인지 대시(-)인지가 다르다. 사용할 리전의 형식은 콘솔의 **정적 웹 사이트 호스팅** 항목에 표시되는 엔드포인트를 그대로 쓰면 된다. 그리고 Requester Pays가 켜진 버킷은 웹사이트 엔드포인트로 접근하면 403 Access Denied가 반환된다.

## 설정: 인덱스 문서, 오류 문서, 공개 읽기

버킷의 **속성 → 정적 웹 사이트 호스팅**에서 이 버킷을 웹사이트로 사용하도록 활성화한다.

- **인덱스 문서(필수):** `index.html`처럼 루트와 하위 폴더 요청에 돌려줄 파일 이름. 대소문자를 구분하고, 실제로 업로드한 파일 이름과 정확히 일치해야 한다.
- **오류 문서(선택):** 4XX 오류가 났을 때 보여줄 `404.html` 같은 파일. 지정하지 않으면 S3의 기본 오류 페이지가 나온다.
- **리다이렉션 규칙(선택):** 객체 키나 접두사 조건에 따라 다른 곳으로 보내는 JSON 규칙.

웹사이트 엔드포인트는 공개 읽기만 지원하므로, 이 설정만으로는 접속되지 않는다. 버킷이 기본적으로 비공개이기 때문이다. 그래서 두 가지를 추가로 바꿔야 한다.

1. **퍼블릭 액세스 차단 해제:** 버킷의 **권한 → 퍼블릭 액세스 차단(버킷 설정)** 에서 "모든 퍼블릭 액세스 차단"을 끈다. 계정 수준 차단이 켜져 있다면 그것도 풀어야 버킷 정책을 저장할 수 있다.
2. **버킷 정책으로 읽기 허용:** 모든 주체에게 `s3:GetObject`를 허용한다.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "PublicReadGetObject",
      "Effect": "Allow",
      "Principal": "*",
      "Action": ["s3:GetObject"],
      "Resource": ["arn:aws:s3:::<버킷-이름>/*"]
    }
  ]
}
```

이 정책은 버킷 안의 모든 객체를 인터넷 누구에게나 공개한다. 공개해도 되는 파일만 이 버킷에 두어야 하고, 정적 사이트 전용 버킷을 따로 만드는 것이 안전하다. AWS 문서도 가능하다면 퍼블릭 액세스 차단을 유지하라고 권고하는데, 그 방법이 바로 뒤에서 나올 CloudFront와 OAC 조합이다.

## 개념: 도메인 연결과 HTTPS

웹사이트 엔드포인트 주소는 `my-site.s3-website.ap-northeast-2.amazonaws.com`처럼 길고 외우기 어렵다. 이 주소 자체를 바꿀 수는 없지만, **Route 53** 으로 내 도메인을 연결할 수 있다. 다만 S3 자체는 HTTPS를 지원하지 않기 때문에, HTTPS가 필요하면 **CloudFront** 를 앞에 두어야 한다.

### Route 53으로 도메인 연결하기

Route 53에서 **A 레코드의 별칭(Alias)** 으로 S3 웹사이트 엔드포인트를 가리키게 만든다. 별칭 레코드는 CNAME과 비슷하게 동작하지만 루트 도메인(`example.com`)에도 쓸 수 있다는 점이 다르다. CNAME은 서브도메인에만 쓸 수 있다. Route 53은 S3 같은 AWS 리소스로 향하는 별칭 쿼리에는 요금을 부과하지 않는다.

여기서 주의할 점이 하나 있다. **버킷 이름이 도메인 이름과 같아야 한다.** `www.example.com`으로 접속하게 하려면 버킷 이름도 `www.example.com`이어야 한다. 루트 도메인과 `www`를 모두 쓰고 싶다면 버킷을 각각 만들고, 한쪽은 다른 쪽으로 리다이렉트하도록 설정한다. 버킷 이름은 전 세계에서 유일해야 하므로, 이미 다른 사람이 그 이름의 버킷을 가지고 있다면 해당 이름으로는 이 방식을 쓸 수 없다. Route 53에서 대상 상태 평가(Evaluate target health)는 아니오로 둔다.

### CloudFront로 HTTPS 적용하기

S3 웹사이트 엔드포인트는 HTTPS를 지원하지 않는다. 브라우저가 HTTPS로 접속하게 하려면 CloudFront 배포를 S3 앞에 두고, Route 53 레코드는 S3가 아닌 CloudFront를 가리키게 한다. 이 구성은 HTTPS 외에 전 세계 엣지에서의 캐싱이라는 이점도 준다. 정적 콘텐츠가 캐싱에 적합하다고 앞에서 정리한 이유가 여기서 이어진다.

CloudFront에 OAC(Origin Access Control)를 쓰면 버킷의 퍼블릭 액세스 차단 네 가지를 모두 켠 채로, CloudFront만 객체를 읽게 만들 수 있다. 앞서 본 "버킷 전체 공개" 정책을 피할 수 있으므로 실무에서는 이 구성이 권장된다. AWS 문서는 AWS Amplify Hosting을 가장 쉬운 방법으로 안내하기도 한다. Amplify Hosting은 CloudFront 기반 CDN으로 S3 콘텐츠를 HTTPS 공개 URL로 제공한다.

## 용어 정리

| 용어 | 설명 |
|---|---|
| **정적 콘텐츠** | 모든 사용자에게 동일하게 전달되는 파일. 캐싱 가능 |
| **동적 콘텐츠** | 시간·사용자·입력에 따라 달라지며 서버 연산이 필요한 콘텐츠 |
| **정적 웹 호스팅** | 버킷의 정적 파일을 서버 없이 웹사이트로 서비스하는 S3 기능 |
| **웹사이트 엔드포인트** | 정적 호스팅용 주소. HTTP만, 공개 읽기만, GET/HEAD만 지원 |
| **REST API 엔드포인트** | SDK·CLI가 쓰는 일반 주소. HTTPS와 비공개 접근 지원 |
| **인덱스 문서** | 루트·폴더 요청에 반환하는 문서. 설정 필수 |
| **오류 문서** | 4XX 오류 시 반환하는 문서. 설정 선택 |
| **별칭(Alias) 레코드** | Route 53의 AWS 리소스 연결용 레코드. 루트 도메인에도 사용 가능 |
| **OAC** | CloudFront만 S3 객체를 읽도록 하는 Origin Access Control |
