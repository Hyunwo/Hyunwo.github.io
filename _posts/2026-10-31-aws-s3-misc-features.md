## 개념: 서버 액세스 로깅

**서버 액세스 로깅(Server Access Logging)** 은 버킷으로 들어온 요청을 기록해서 다른 버킷에 로그 파일로 저장하는 기능이다. 누가, 언제, 어떻게 접근했는지 남기므로 보안 감사, 접근 패턴 분석, 디버깅에 쓴다.

핵심은 **기록 대상 버킷(소스)과 로그를 저장하는 버킷(대상)을 분리**하는 것이다. 같은 버킷에 로그를 저장하면 로그 파일이 쓰일 때마다 그 쓰기 요청이 다시 로그로 기록되고, 그 로그가 또 기록되는 무한 루프가 생긴다. 문서에 따르면 소스 버킷을 대상으로 지정하는 것이 기술적으로 막혀 있지는 않지만 권장되지 않고, 이 루프가 발생한다고 경고한다.

대상 버킷에는 몇 가지 조건이 있다.

- 소스 버킷과 **같은 리전, 같은 계정**에 있어야 한다. 다른 계정으로 보내려면 CloudTrail 같은 다른 경로를 써야 한다.
- 기본 암호화는 **SSE-S3** 여야 한다. SSE-KMS를 쓰면 로그 전달이 정상 동작하지 않을 수 있다.
- Object Lock이 켜진 버킷이나 Requester Pays 버킷은 대상이 될 수 없다.
- 로그 전달 서비스(`logging.s3.amazonaws.com`)에 `s3:PutObject`를 허용하는 버킷 정책이 필요하다. 콘솔에서 켜면 자동으로 추가된다.

한 가지 기억할 점은 로그 전달이 **최선 노력(best-effort)** 이라는 것이다. 대부분의 요청은 기록되지만 완전성과 적시성이 보장되지 않아서, 로그가 몇 시간 늦게 도착하거나 드물게 누락되거나 중복될 수 있다. 모든 요청의 정확한 회계 장부가 필요하다면 서버 액세스 로그만 믿어서는 안 된다. 켜는 것 자체에는 추가 요금이 없고, 저장된 로그 파일의 스토리지 비용만 발생한다.

## 개념: 이벤트 알림

**이벤트 알림(Event Notifications)** 은 객체가 생성되거나 삭제되는 등의 일이 생겼을 때 다른 서비스를 자동으로 호출하는 기능이다. 이미지가 올라오면 썸네일을 만들고 싶다고 하자. 이벤트 알림이 없다면 누군가가 계속 버킷을 들여다보며 새 파일이 올라왔는지 확인해야 한다. 이벤트 알림을 쓰면 업로드가 끝나는 순간 Lambda 같은 서비스가 바로 실행된다. Lambda는 서버 없이 코드만 실행하는 서버리스 컴퓨팅 서비스다.

호출할 수 있는 대상은 다음과 같다. 하나의 알림에는 대상을 하나만 지정할 수 있다.

| 대상 | 조건 |
|---|---|
| **SNS** | 표준 토픽, 버킷과 같은 리전. FIFO 토픽은 미지원 |
| **SQS** | 버킷과 같은 리전. FIFO 큐는 미지원 |
| **Lambda** | 버킷과 같은 리전 |
| **EventBridge** | 버킷 단위로 켜고 끔. 켜면 모든 이벤트가 전달되고, EventBridge 규칙으로 여러 대상에 보낼 수 있음 |

SNS, SQS, Lambda는 S3가 호출할 수 있도록 대상 쪽에 권한을 따로 부여해야 한다. FIFO 큐로 보내야 한다면 EventBridge를 경유하는 방법을 쓴다.

이벤트 종류는 `ObjectCreated`(Put, Post, Copy, 멀티파트 완료), `ObjectRemoved`(Delete, DeleteMarkerCreated), `ObjectRestore`, `ObjectTagging`, `Replication`, `LifecycleExpiration` 등으로 나뉜다. 다만 **수명 주기 규칙으로 자동 삭제된 경우는 `ObjectRemoved`가 아니라 `LifecycleExpiration` 이벤트**로 따로 받아야 한다. 알림은 **최소 한 번 전달**이 원칙이라 중복이 올 수 있고 순서도 보장되지 않으므로, 받는 쪽에서 중복과 순서 뒤바뀜을 견디게 만들어야 한다.

썸네일 예시에서 주의할 점도 있다. Lambda가 만든 썸네일을 **같은 버킷에 다시 쓰면** 그 쓰기가 또 이벤트를 일으켜 실행이 반복될 수 있다. 문서는 버킷을 둘로 나누거나 트리거를 특정 접두사로 제한하라고 안내한다. 로깅에서 본 무한 루프와 같은 종류의 문제다.

## 개념: 복제

**복제(Replication)** 는 버킷에 생긴 변경 내용을 다른 버킷으로 **비동기**로 자동 복사하는 기능이다. 대상 버킷은 다른 리전이어도, 다른 계정이어도 된다.

- **CRR(Cross-Region Replication):** 다른 리전의 버킷으로 복제. 사용자와 가까운 곳에 데이터를 두거나, 법적·정책적 이유로 리전을 나눠 보관하거나, 재해 대비 백업을 둘 때 쓴다.
- **SRR(Same-Region Replication):** 같은 리전의 다른 버킷으로 복제. 로그를 한곳에 모으거나 운영·테스트 계정 간 데이터를 동기화할 때 쓴다.

복제를 쓰려면 **소스와 대상 버킷 모두 버저닝이 켜져 있어야 한다.** 복제가 설정된 동안에는 소스 버킷의 버저닝을 끌 수 없고, 대상 버킷의 버저닝을 끄면 복제가 `FAILED` 상태가 된다. 대상 버킷은 Requester Pays일 수 없다. 소스 버킷에 Object Lock이 있으면 대상 버킷에도 있어야 한다.

무엇이 복제되고 무엇이 복제되지 않는지가 가장 많이 헷갈린다.

| 상황 | 복제 여부 |
|---|---|
| 규칙을 만든 이후에 생성·갱신된 객체 | 복제됨 |
| 규칙을 만들기 전부터 있던 객체 | **복제되지 않음.** S3 Batch Replication으로 따로 복제 |
| 삭제 마커(delete marker) | 최신 형식의 복제 구성에서는 **기본적으로 복제되지 않음.** 태그 기반이 아닌 규칙에서 켤 수 있음 |
| 버전 ID를 지정한 영구 삭제 | **복제되지 않음.** 소스에서만 지워짐 |
| 복제로 만들어진 복제본의 재복제 (A→B→C) | 복제되지 않음. Batch Replication 필요 |
| 수명 주기 규칙이 수행한 동작 | 복제되지 않음. 양쪽에 같은 규칙을 설정 |
| Glacier Flexible Retrieval, Deep Archive 등 아카이브 객체 | 복원해서 다른 스토리지 클래스로 복사하기 전에는 복제되지 않음 |

강의에서 "삭제를 막고도 복제가 가능하다"고 한 것은 **삭제 마커 복제** 옵션을 말한다. 소스 버킷에서 삭제 마커가 생겼을 때 이를 대상에도 만들지 말지 정하는 설정이다. 영구 삭제가 복제되지 않는 것은 악의적인 삭제로부터 데이터를 보호하기 위한 동작이다.

속도에 대해서는 SLA가 걸린 옵션이 따로 있다. **S3 Replication Time Control(RTC)** 은 새 객체 대부분을 15분 이내에 복제하는 것을 SLA로 보장한다. 이 옵션이 없는 일반 복제는 SLA가 없다.

## 개념: Transfer Acceleration

**Transfer Acceleration** 은 멀리 떨어진 클라이언트와 S3 버킷 사이의 전송 속도를 높이는 버킷 단위 기능이다. 클라이언트가 가까운 **CloudFront 엣지 로케이션**으로 데이터를 보내면, 거기서부터는 AWS의 최적화된 네트워크 경로로 S3까지 전달된다. 예를 들어 한국의 사용자가 미국 버킷에 대용량 파일을 올릴 때처럼 거리가 멀수록 효과가 크다.

여기서 CloudFront는 경로의 일부로 엣지 로케이션을 활용할 뿐, 콘텐츠를 캐싱해서 보여주는 CDN과는 다른 기능이다. 이 기능은 클라이언트와 버킷 사이의 **전송 경로**를 최적화하는 것이다.

사용 조건은 다음과 같다.

- 버킷에서 기능을 켜야 하고, 켠 뒤 속도 개선이 나타나기까지 최대 20분이 걸릴 수 있다.
- 전용 엔드포인트 `<버킷-이름>.s3-accelerate.amazonaws.com`을 써야 한다. 일반 엔드포인트도 계속 동작한다.
- 버킷 이름은 DNS 규칙에 맞아야 하고 **마침표(.)가 들어갈 수 없다.**
- 가상 호스트 방식 요청만 지원한다.
- 일부 리전에서만 지원한다.
- 추가 데이터 전송 요금이 붙을 수 있으므로 [요금표](https://aws.amazon.com/s3/pricing/)를 확인한다.

## 개념: Requester Pays

버킷 소유자가 내려받기 비용을 내는 것이 기본이다. **Requester Pays** 를 켜면 객체를 가져가는 **요청자가 요청 비용과 데이터 전송 비용을 부담**한다. 기업 간에 데이터를 공유하거나 연구용 대용량 데이터를 공개할 때, "가져가는 쪽이 비용을 내라"는 방식으로 비용 문제를 풀 수 있다. 저장 비용은 항상 버킷 소유자가 낸다.

몇 가지 규칙이 있다.

- **익명 접근은 불가능하다.** 요청자를 식별해서 비용을 청구해야 하므로 모든 요청이 인증되어 있어야 한다. 그래서 앞 글에서 본 웹사이트 엔드포인트로 접근하면 403 Access Denied가 반환된다.
- 요청자는 요청마다 비용 부담에 동의한다는 표시로 `x-amz-request-payer` 헤더를 보낸다. AWS CLI에서는 `--request-payer requester` 옵션을 쓴다.
- 요청자가 IAM 역할을 사용하면 그 역할을 소유한 계정에 비용이 청구된다.
- 요청이 `403 AccessDenied`로 끝났는데 버킷 소유자의 계정이나 조직 안에서 시작된 요청이라면 소유자에게 청구된다.
- 서버 액세스 로깅의 대상 버킷과 복제의 대상 버킷으로는 쓸 수 없다.

## 용어 정리

| 용어 | 설명 |
|---|---|
| **서버 액세스 로깅** | 버킷에 대한 요청을 다른 버킷에 로그로 저장하는 기능. 최선 노력 전달 |
| **이벤트 알림** | 객체 생성·삭제 등의 이벤트로 SNS, SQS, Lambda, EventBridge를 호출하는 기능 |
| **Lambda** | 서버 없이 코드를 실행하는 AWS 서버리스 컴퓨팅 서비스 |
| **복제(Replication)** | 변경 내용을 다른 버킷으로 비동기 복사. 양쪽 버저닝 필수 |
| **CRR / SRR** | 다른 리전 복제 / 같은 리전 복제 |
| **삭제 마커 복제** | 소스의 삭제 마커를 대상에도 만들지 정하는 복제 옵션. 기본은 꺼짐 |
| **S3 Batch Replication** | 기존 객체나 복제본을 온디맨드로 복제하는 작업 |
| **S3 RTC** | 복제를 15분 이내로 보장하는 유료 옵션 |
| **Transfer Acceleration** | 가까운 CloudFront 엣지를 거쳐 업로드·다운로드 전송 경로를 최적화하는 기능 |
| **Requester Pays** | 요청 비용과 데이터 전송 비용을 요청자가 부담하는 모드. 인증 필수 |
