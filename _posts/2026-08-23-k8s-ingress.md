오늘은 Ingress였다. Pod와 Service만으로는 해결이 안 되는, 경로 기반 라우팅과 무중단 배포 이야기다.

> **참고**: 강의에서 예시로 든 커뮤니티 Nginx Ingress Controller(`kubernetes/ingress-nginx`)는 2026년 3월 31일부로 은퇴해서 더 이상 보안 패치·업데이트가 안 나온다. Ingress API 자체(`networking.k8s.io/v1`)는 계속 정상 지원되고, 아래 개념도 전부 그대로 유효하다. 다만 지금 새로 설치한다면 후속 표준인 Gateway API나 Kong 같은 다른 컨트롤러를 쓰는 게 맞다.

---

## Ingress를 쓰는 이유 1: 서비스 로드밸런싱

쇼핑몰을 예로 들면, 쇼핑 페이지·고객센터·주문 서비스를 각각 별도 Pod로 나눠서 만든다. 이렇게 나누면 쇼핑 페이지에 문제가 생겨도 고객 응대나 주문 처리에는 영향이 없다는 장점이 있다.

문제는 사용자가 `w.mall.com`(쇼핑), `w.mall.com/customer`(고객센터), `w.mall.com/order`(주문)처럼 경로별로 다른 서비스에 접근하게 하려면, 원래는 이 경로를 보고 알맞은 서비스로 트래픽을 나눠주는 **L4/L7 스위치 장비**가 따로 필요하다. **Ingress가 이 역할을 대신해준다.**

![Ingress 요청 흐름]({{ site.baseurl }}/assets/images/k8s-ingress/ingress_flow.png)

Ingress 오브젝트 자체는 "이 host의 이 path로 오면 이 Service로 보내라"는 **규칙표**일 뿐이다. 이 규칙을 실제로 실행해주는 **구현체(Ingress Controller)**가 따로 있어야 동작한다. Ingress만 만들어놓고 아무것도 설치 안 하면, 이 규칙은 그냥 텍스트로만 존재하고 아무 일도 안 일어난다.

Ingress Controller(예: Nginx 계열)를 설치하면 Deployment로 실제 Pod가 뜨고, 이 Pod가 Ingress 규칙을 계속 보고 있다가 그 규칙대로 트래픽을 해당 Service로 넘겨준다. 그리고 외부에서 이 Controller Pod에 접근할 수 있도록 NodePort나 LoadBalancer로 노출시켜야 한다.

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: mall-ingress
spec:
  rules:
    - host: w.mall.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: svc-shop
                port:
                  number: 80
          - path: /customer
            pathType: Prefix
            backend:
              service:
                name: svc-customer
                port:
                  number: 80
          - path: /order
            pathType: Prefix
            backend:
              service:
                name: svc-order
                port:
                  number: 80
```

## Ingress를 쓰는 이유 2: Canary 업그레이드

v1이 서비스되고 있는 상태에서 v2 Pod와 Service를 새로 띄우고, 같은 host(`w.app.com`)를 가리키는 Ingress를 하나 더 만든 뒤 annotation을 추가하면 트래픽의 일부만 v2로 흘려보낼 수 있다.

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: app-canary
  annotations:
    nginx.ingress.kubernetes.io/canary: "true"
    nginx.ingress.kubernetes.io/canary-weight: "10"
spec:
  rules:
    - host: w.app.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: svc-v2
                port:
                  number: 80
```

특정 헤더 값(예: 언어가 `KR`일 때만)에 따라 트래픽을 몰아줄 수도 있다.

**여기서 중요한 포인트**: 이 `canary-weight`, `canary-by-header` 같은 옵션은 **표준 Ingress 스펙이 아니라 Nginx Controller 전용 annotation**이다. 그래서 Controller를 다른 걸로 바꾸면 이 설정이 그대로 안 먹힌다. 이게 바로 Gateway API가 등장한 핵심 이유 중 하나다 — Gateway API의 `HTTPRoute`는 이런 가중치 기반 트래픽 분할과 헤더 매칭을 **표준 스펙으로 정의**해서, 어떤 구현체(Envoy, Istio, Cilium 등)를 쓰든 똑같이 동작한다.

## HTTPS 연결: TLS

Pod 자체에서 인증서 기능을 처리하기 어려울 때, Ingress 단에서 HTTPS를 처리해줄 수 있다. Ingress Controller는 443 포트로 별도 연결을 받고, Ingress에 `tls` 옵션으로 인증서가 담긴 Secret을 연결하면 된다.

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: mall-ingress-tls
spec:
  tls:
    - hosts:
        - w.mall.com
      secretName: mall-tls-secret
  rules:
    - host: w.mall.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: svc-shop
                port:
                  number: 80
```

## 용어 정리

| 용어 | 설명 |
|---|---|
| **Ingress** | host/path 규칙에 따라 트래픽을 알맞은 Service로 연결해주는 오브젝트. 실제 동작은 Controller가 처리 |
| **Ingress Controller** | Ingress 규칙을 실제로 실행하는 구현체(Pod). Nginx, Kong 등이 대표적 |
| **ingress-nginx** | 커뮤니티가 관리하던 오픈소스 Nginx Ingress Controller. 2026년 3월 31일 공식 은퇴 |
| **Gateway API** | Ingress의 한계(vendor annotation 의존)를 해결한 쿠버네티스 공식 후속 표준. Canary·헤더 라우팅을 표준 스펙으로 지원 |
| **canary-weight** | Nginx Ingress Controller 전용 annotation. 지정한 비율만큼 트래픽을 다른 버전으로 분배 |
| **TLS (Ingress)** | Ingress 단에서 HTTPS를 처리하도록 인증서가 담긴 Secret을 연결하는 설정 |
