8/14, 8/17에서 Authentication("누구세요?")을 다뤘다면, 오늘은 Authorization — 그중에서도 제일 많이 쓰는 **RBAC(Role-Based Access Control)**를 정리한다. "권한이 있는지"를 역할(Role) 기반으로 판단하는 방식이다.

## 핵심 오브젝트 4개

RBAC는 오브젝트 4개의 조합으로 이해하면 된다.

- **Role**: 한 Namespace 안에서 "무엇을 할 수 있는지" 정의 (예: Pod 조회만 가능)
- **RoleBinding**: Role과 ServiceAccount(또는 User)를 연결. **한 Namespace 안에서만** 유효
- **ClusterRole**: Role과 기능은 똑같은데, **클러스터 단위 자원**(Node, PV 등)까지 지정할 수 있음
- **ClusterRoleBinding**: ClusterRole과 연결하는데, **클러스터 전체**에 적용됨

여기서 헷갈리는 부분이 하나 있다. **ClusterRole이라고 해서 무조건 클러스터 전체에 권한이 퍼지는 게 아니다.** 실제로 범위를 결정하는 건 Role/ClusterRole이 아니라 **어떤 Binding으로 연결했는지**다.

![Role/ClusterRole × RoleBinding/ClusterRoleBinding 조합]({{ site.baseurl }}/assets/images/k8s-rbac/rbac_matrix.png)

- **Role + RoleBinding**: 가장 기본. 이 Namespace 안에서만 적용
- **Role + ClusterRoleBinding**: 애초에 불가능한 조합이다. ClusterRoleBinding은 ClusterRole만 참조할 수 있다
- **ClusterRole + RoleBinding**: ClusterRole의 권한 "정의"만 가져다 쓰고, 실제 적용 범위는 그 RoleBinding이 있는 Namespace로 한정된다
- **ClusterRole + ClusterRoleBinding**: 모든 Namespace + 클러스터 단위 자원까지 접근 가능. 사실상 admin 권한을 줄 때 쓰는 조합

---

## 왜 굳이 "ClusterRole + RoleBinding" 조합을 쓸까

세 번째 조합("ClusterRole + RoleBinding")이 제일 헷갈리는데, 실무에서 꽤 유용하게 쓰인다. 예를 들어 "모든 Namespace에서 Pod는 조회만 가능하게 하자"는 규칙을 여러 Namespace에 똑같이 적용하고 싶다고 하자.

Namespace마다 똑같은 내용의 Role을 하나씩 만들면, 나중에 권한 내용을 바꿔야 할 때 **모든 Namespace의 Role을 일일이 찾아서 고쳐야** 한다. 이건 관리하기 번거롭고 실수하기도 쉽다.

![여러 Namespace가 하나의 ClusterRole을 재사용]({{ site.baseurl }}/assets/images/k8s-rbac/clusterrole_reuse.png)

대신 **ClusterRole을 하나만 만들어두고**, 각 Namespace의 RoleBinding이 이 ClusterRole을 참조하게 하면, 권한 내용이 바뀔 때 **ClusterRole 하나만 고치면 모든 Namespace에 반영**된다. 각 RoleBinding은 여전히 자기 Namespace 범위로만 적용되니, "권한 정의는 공유하되, 적용 범위는 각자 다르게" 가져가는 실용적인 패턴이다.

## Role/ClusterRole 내부 구조

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: pod-reader
  namespace: default
rules:
  - apiGroups: [""]        # Pod는 core API라 빈 문자열
    resources: ["pods"]
    verbs: ["get", "list"]
  - apiGroups: ["batch"]   # Job은 batch API 그룹
    resources: ["jobs"]
    verbs: ["get", "list"]
```

- **apiGroups**: 어느 API 그룹인지. Pod, Service 같은 core 자원은 빈 문자열(`""`)이고, Job처럼 별도 그룹에 속한 자원은 그 그룹 이름(`batch`)을 넣어야 한다
- **resources**: 대상 자원 종류
- **verbs**: 허용할 동작(`get`, `list`, `create`, `update`, `delete` 등)

이렇게 만든 Role을 RoleBinding으로 ServiceAccount와 연결한다.

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: pod-reader-binding
  namespace: default
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
subjects:
  - kind: ServiceAccount
    name: default
    namespace: default
```

`roleRef`는 하나만 지정할 수 있지만, `subjects`는 여러 ServiceAccount(또는 User)를 한 번에 연결할 수 있다.

클러스터 전체 자원까지 admin처럼 다 접근하게 하려면 ClusterRole + ClusterRoleBinding 조합을 쓴다.

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: cluster-admin-like
rules:
  - apiGroups: ["*"]
    resources: ["*"]
    verbs: ["*"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: cluster-admin-binding
roleRef:
  kind: ClusterRole
  name: cluster-admin-like
  apiGroup: rbac.authorization.k8s.io
subjects:
  - kind: ServiceAccount
    name: sa-02
    namespace: nm-02
```

## 참고: 토큰 발급 방식은 최신 버전 기준으로 다르다

강의 자료에는 `ServiceAccount`에 `Secret`이 자동으로 붙어서 그 안에 토큰이 저장되는 것처럼 그려져 있는데, 이건 **Kubernetes 1.23 이전 방식**이다. 지금(1.24+)은 이 Secret이 자동으로 안 생기고, 필요할 때 `kubectl create token <ServiceAccount 이름>`으로 직접 발급받아야 한다. (자세한 배경은 지난 8/17 글 참고) RBAC로 "무엇을 할 수 있는지" 정하는 개념 자체는 토큰 발급 방식과 무관하게 동일하다.

## 용어 정리

| 용어 | 설명 |
|---|---|
| **RBAC** | 역할(Role) 기반으로 API 자원 접근 권한을 관리하는 방식 |
| **Role** | 한 Namespace 안에서 자원별로 허용할 동작을 정의하는 오브젝트 |
| **RoleBinding** | Role과 ServiceAccount/User를 연결. 적용 범위는 자신이 속한 Namespace로 한정 |
| **ClusterRole** | Role과 구조는 같지만 클러스터 단위 자원(Node, PV 등)까지 지정 가능 |
| **ClusterRoleBinding** | ClusterRole과 연결하며, 클러스터 전체(모든 Namespace)에 적용 |
| **apiGroups** | 자원이 속한 API 그룹. core 자원은 빈 문자열, 그 외는 그룹명(예: batch) |
| **verbs** | Role에서 허용하는 동작 (get, list, create, update, delete 등) |
| **roleRef** | RoleBinding/ClusterRoleBinding이 참조하는 Role/ClusterRole 지정 필드 |
| **subjects** | RoleBinding/ClusterRoleBinding에 연결할 ServiceAccount/User 목록 |
